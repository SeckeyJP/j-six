# 設計レビュースキル

J-SIX プロセスの Phase 2（技術設計）で設計レビューを実施する。

## レビュー観点

### 1. Design Spec の品質チェック

`docs/specs/design-spec-*.md` を読み、以下を検証:

- [ ] アーキテクチャ方針が要求 Spec の非機能要件を満たすか（Design Spec 7 章の節が要求 Spec 3.5 の6大項目と対応しているか）
- [ ] 技術選定に理由が記載されているか
- [ ] 代替案が検討されているか（ADR への参照があるか）
- [ ] インターフェース定義が具体的か
- [ ] エラーハンドリング方針が明確か
- [ ] セキュリティ要件への対応が記載されているか

### 2. ADR の網羅性チェック

`docs/adr/` 配下の ADR を確認し、以下を検証:

- [ ] 主要な技術判断に ADR が存在するか
- [ ] 各 ADR に代替案と却下理由が記載されているか
- [ ] ADR のステータスが最新か

### 3. プロトタイプとの整合性（該当する場合）

プロトタイプコードが存在する場合:

- [ ] Design Spec の方針とプロトタイプ実装が一致しているか
- [ ] プロトタイプで判明した技術的課題が Spec に反映されているか

### 4. 合意成熟度（Phase 2 品質ゲートの判定基準）

合意対象ごとに到達レベルを判定する（J-SIX.md Phase 1「合意成熟度による判定」）。

- [ ] Design Spec・ADR・実動プロトタイプ・人手で書く工程成果物が**完成レベル**（双方が確認済み）か
- [ ] 実装から逆生成する工程成果物が、代替物（プロトタイプ・Design Spec の節）で**充実レベル**まで
      確認され、Phase 6 で逆生成版に差し替えることが合意されているか
- [ ] 顧客に提出する設計書の目次（組立定義 `docs/design-docs/assembly-*.md`）が合意されているか

逆生成する成果物が充実レベルに留まることは**指摘事項にしない**（Phase 6 で完成レベルになる設計である）。
指摘するのは、人手で書く合意対象が仕掛レベルのまま残っている場合である。

## 出力フォーマット

レビュー結果を以下の形式で報告:

```markdown
## 設計レビュー結果

**対象**: [Design Spec ファイル名]
**レビュー日**: [日付]
**判定**: [承認 / 条件付き承認 / 差し戻し]

### 合意成熟度

| 合意対象 | 到達レベル | 求められるレベル |
|---|---|---|
| [Design Spec / ADR / 工程成果物 ①… / 組立定義] | [仕掛 / 充実 / 完成] | [完成 / 充実] |

### 指摘事項

#### Critical（修正必須）
- [指摘内容と理由]

#### Warning（修正推奨）
- [指摘内容と理由]

#### Suggestion（検討推奨）
- [指摘内容と理由]

### 不足している ADR
- [記録すべき判断とその理由]
```
