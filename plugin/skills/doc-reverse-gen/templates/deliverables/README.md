# 工程成果物テンプレート（27点）

IPA「[機能要件の合意形成ガイド](https://www.ipa.go.jp/archive/files/000004517.pdf)」が想定する
**工程成果物27点**の空テンプレート。記入済み実例は
[`examples/monthly-billing/docs/deliverables/`](https://github.com/SeckeyJP/j-six/tree/main/examples/monthly-billing/docs/deliverables)
にある（同じディレクトリ構成・同じファイル名なので、並べて見比べられる）。

## この単位で作る理由

IPA 自身が、外部設計工程には業界標準の工程成果物が存在しないこと、および
**工程成果物と設計書は1対1ではない**ことを明記している。

> 外部設計工程には、現時点では業界として標準とされる「工程成果物」が存在しません。
> …設計書の作成単位や構成が、本ガイドで想定している「工程成果物」と一致しないことがあります。
> 例えば、画面編では、「工程成果物」として「画面レイアウト」、「画面入出力項目一覧」、
> 「画面アクション明細」などを想定していますが、実際のプロジェクトでは、これらを合わせて
> １つの「ユーザインタフェース設計書」として作成する場合があります。
> — 同ガイド 概要編 2.1

したがって「基本設計書」のような大きな単位ではなく**工程成果物の粒度**で作り、
顧客の様式に応じて束ねる。束ね方は [`assembly/`](assembly/GUIDE.md) に定義する。

## 由来の内訳

| 由来 | 件数 | 乖離リスク |
|---|---|---|
| コードから逆生成 | 18 | 抽出・記述・更新漏れを確認する |
| 受入テストから逆生成 | 1 | テストが確認する範囲・記述・対象版を確認する |
| コード＋Spec／ADR の併用 | 3 | 一部残る |
| Spec / CLAUDE.md（人手） | 5 | 残る |

27点中19点が実物から自動で起こせる。人手由来の5点に加え、併用3点のSpec/ADR部分も人手で維持する。逆生成した19点にも人間の確認が必要である。これが J-SIX の3層ドキュメント戦略の主張そのものである。

## 使い方

1. 必要な領域のディレクトリを `docs/deliverables/` にコピーする
2. 各ファイルの冒頭（対象・版・日付・逆生成元）を埋める
3. `[TODO: ...]` を埋める
4. 末尾の「記入ガイド（記入後は削除する）」の節を削除する

### 作る順序

人手で書く成果物が、逆生成する成果物の前提になる。この順で作る。

```
Phase 1-2  要求 Spec / Design Spec / ADR
    ↓
  ① システム化業務一覧・② 業務フロー・④ 共通ルール（人手。合意の対象）
    ↓
Phase 3-4  hold-out 受入テスト → 実装
    ↓
  ③ システム化業務説明（受入テストから逆生成）
    ↓
Phase 6  ⑤〜㉗（コードから逆生成）
```

### 27点すべてを作る必要はない

対象システムが持たない領域は作らない。API のみのシステムなら画面6点・帳票5点・バッチ4点は
該当しない（[`examples/approval-workflow/`](https://github.com/SeckeyJP/j-six/tree/main/examples/approval-workflow) がその例）。
**作らない領域は「該当なし」と記録する。**空欄のまま放置すると、抜けなのか対象外なのかが
区別できなくなる。

### 顧客の様式に合わせる

工程成果物と設計書は1対1ではない。顧客が「ユーザインタフェース設計書」のような
大きな単位を求める場合は、該当する工程成果物（画面③④⑤など）を束ねて提出する。
束ね方は [`assembly/`](assembly/GUIDE.md) に定義してある。

| ファイル | 内容 |
|---|---|
| [`assembly/GUIDE.md`](assembly/GUIDE.md) | 組立の原則（正は工程成果物、設計書はビュー）、事前提出と納品の2時期、顧客様式への組み替え手順 |
| [`assembly/kihon-sekkei.md`](assembly/kihon-sekkei.md) | 基本設計書の組立例（27点すべて＋Spec＋ADR。章ごとの事前提出可否） |
| [`assembly/shousai-sekkei.md`](assembly/shousai-sekkei.md) | 詳細設計書の組立例（IPA 27点の範囲外。コード・PROP・ADR から逆生成） |

## 合意成熟度

IPA ガイドは合意形成を3段階に分けている（同ガイド 3.1.1）。

| レベル | 定義 |
|---|---|
| 仕掛レベル | 発注者が「言い切った」、開発者が「聞き切った」 |
| 充実レベル | 図表に書いてレビューを繰り返し、合意内容が充実する |
| 完成レベル | 合意内容が管理され、双方が確認できた |

J-SIX では成熟度を**成果物ごと**に判定し、Phase 1・2・6 の品質ゲートの到達基準にしている
（J-SIX.md Phase 1「合意成熟度による判定」）。27点については次のとおり。

| 成果物 | Phase 2 設計レビューでの到達 | 完成レベルになる時点 |
|---|---|---|
| 人手で書く5点（①②④⑩㉒） | 完成レベル | Phase 2 |
| 併用の3点（⑱㉔㉗） | Spec・ADR 由来の部分は完成、残りは充実 | Phase 6 |
| 逆生成する19点 | 充実レベル（プロトタイプ等の代替物で確認） | Phase 6 |

逆生成する19点も、対象版に対する内容の一致・網羅性を確認する。テスト通過は文章や図の正しさを保証しない。
完成レベルの条件は「双方が確認できた」ことであり、Phase 6の納品物レビューで確認する。
