# 証跡パッケージ生成スキル

J-SIX Phase 4 の **G4** で、G1〜G3 の結果を人間レビュー用・顧客納品用に構造化する。

日本の SI では「品質が良い」ことと「品質が良いと**示せる**」ことは別の要件である。
このスキルは後者を担う。

## 最重要ルール: 3区分を混ぜない

| 区分 | 内容 | 出力ファイル | 納品時の扱い |
|---|---|---|---|
| **証跡（Evidence）** | 決定論的検証の生出力と集計 | `01`〜`05`, `evidence.json`, `env.json` | 納品可。再現情報を必ず添付 |
| **参考所見（Advisory）** | LLM judge の判定・**あなたが書く要約** | `06`, `00` の要約節 | 「AI による参考所見」と明記。**単独で品質判定の根拠にしない** |
| **承認（Approval）** | 人間レビュアーの確認欄・指摘・是正記録 | `07` | 人間が記入する |

参考所見を証跡と分けるのは、LLM の判定が再実行で同じ結果になるとは限らず、
第三者が同じ手順で確かめられないためである。固定した生出力の集計は再計算できるが、再実行結果は環境・乱数・外部依存で変わりうる。実行条件と結果を保存する。

## 手順

### 1. 証跡を生成する（決定論的部分）

通常は G4 として `jsix_run_checks.py` から自動実行される。手動で生成する場合:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/jsix_run_checks.py" --json reports/gate.json
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/jsix_evidence_pack.py" \
  --results reports/gate.json --out reports/evidence/
```

出力先は `reports/evidence/<タスクID>/`。タスクIDは `JSIX_TASK_ID` →
最新の `jsix/red-*` タグ → `untagged` の順で決まる。

### 2. 証跡を読む

**この時点で数値は確定している。** 以下を読み、あなた自身では計算し直さない。

| ファイル | 読み取るもの |
|---|---|
| `evidence.json` | 全ゲートの機械可読な結果 |
| `01_traceability.md` | 未トレースの REQ / PROP |
| `02_test_results.md` | テスト件数・失敗・スキップ、hold-out の結果 |
| `03_coverage_mutation.md` | カバレッジ、mutation score、**生存ミュータント** |
| `04_security.md` | SARIF の severity 別件数 |
| `05_scope_and_integrity.md` | スコープ検査、テスト改変検出の増減 |
| `06_judge_advisory.md` | G3 judge の判定と理由 |

### 3. 要約を書く（参考所見）

`00_summary.md` の「変更概要・リスク箇所・計画からの逸脱（参考所見）」節にある
`_（未記入）_` を、以下の3点に置き換える。

```markdown
### 変更概要

[このタスクで何が変わったかを2〜4文。diff から書く]

### リスク箇所

| # | 箇所 | 根拠となる証跡 |
|---|---|---|
| 1 | `app/workflow.py:120-140` | 生存ミュータント3件（03_coverage_mutation.md） |
| 2 | `app/models.py:72` | カバレッジ未到達（03_coverage_mutation.md） |

### 計画からの逸脱

[タスク定義の受入条件・許可ファイル範囲と実際の差分。無ければ「なし」]
```

**書くときのルール**:

1. **数値は証跡から引用する。** 自分で数え直さない、推定しない
2. リスク箇所には**根拠となる証跡ファイル名**を必ず添える
3. 「良さそう」「問題なさそう」といった評価を書かない。判定は G1〜G3 が済ませている
4. 生存ミュータントとカバレッジ未到達行は、リスク箇所の第一候補になる
   （テストが通っているのに振る舞いが固定されていない箇所だから）
5. 逸脱が無いなら「なし」と書く。無理に何かを見つけない

### 4. 納品前の確認

顧客に納品する場合は以下を確認する。

- [ ] `00_summary.md` の要約節が `_（未記入）_` のままになっていない
- [ ] 参考所見（`06` と `00` の要約節）に「AI による参考所見」の明記がある
- [ ] `07_approval.md` に人間の承認者・日付が記入されている
- [ ] `env.json` に commit SHA・ツール名と版・実行日時・設定ハッシュが入っている
- [ ] 絶対パス（社内のディレクトリ構成）が残っていない

`07_approval.md` が空のまま納品しないこと。**参考所見は承認の代わりにならない。**

## 従来納品物への変換（Phase 6）

`doc-reverse-gen` SkillでMarkdown納品物を作る。Excel/Wordは案件ごとに変換手段を用意し、内容と表示を確認する。専用変換器とその品質をPluginが保証するものではない。

| 従来納品物 | 元データ |
|---|---|
| 単体テスト仕様書・結果報告書 | `01`, `02` |
| 品質報告書 | `03`, `05` ＋ `quality-metrics` の集計 |
| セキュリティ診断結果 | `04` |
| トレーサビリティマトリクス | `01` |
| レビュー記録 | `06`（参考所見）, `07`（承認） |

## 禁止事項

- 証跡（`01`〜`05`, `evidence.json`, `env.json`）を手で編集する
- 証跡に無い数値を要約に書く
- 参考所見に合否判定を書く
- `07_approval.md` を AI が記入する（人間の領域）
