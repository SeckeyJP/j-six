# TDD サイクル管理スキル

J-SIX プロセスの Phase 4（TDD 実装）で、TDD サイクルと**順序固定の4層品質ゲート**を管理する。

## 前提条件

- Phase 3 で承認されたタスク定義が存在すること。以下を含む:
  - タスクID と名称
  - 受入条件（検証可能な形式）と対応する `REQ-nnn` / `PROP-nnn`
  - **変更許可ファイルの範囲**（allow / deny。G1 スコープ検査が使う）
- CLAUDE.md が整備済みであること
- `.jsix-checks.json` にゲートの設定があること（無い場合は Step 0 で作る）

## 全体の流れ

```
🟣 HOLD-OUT → 🔴 RED → 🟢 GREEN → 🔵 REFACTOR → G1 → G2 → G3 → G4
                 │                                  ↑
              RED タグ ─────────────────────────────┘
              （テスト改変検出の基準点）
```

ゲートは**順序固定**で、後段は前段を通過した場合のみ実行する。
G3省略が事前に人間の確認した方針として決まっている構成はG1→G2→G4とし、最大L3で結果監督を維持する。
省略をPASSとして記録せず、実施済みG3のREJECTを省略へ読み替えない。以下のG3手順はG3有効構成に適用する。

---

## Step 0: タスク確認とゲート設定

タスク定義を確認する:
- 受入条件が検証可能な形式か
- 対応する `REQ-nnn` / `PROP-nnn` が特定できるか
- **変更許可ファイルの範囲が定義されているか**（無ければ人間に確認する。
  自律実行が始まってから CC 自身が範囲を広げられるなら検査の意味がない）

`.jsix-checks.json` に `gates.g1.scope.allow` としてタスクの許可範囲を設定する。

**タスク定義をファイルに保存し、Hold-out より前にコミットする。**保存先は
`docs/tasks/<タスクID>.md`。G3 の scope-judge はこのファイルを判定の基準にする
（保存しないと、判定役がコミットメッセージからタスク定義を推測することになる）。
実装中にタスク定義を書き換えないこと。変える必要が出たら人間に確認する。

```markdown
# <タスクID>: <名称>

**対象要件**: REQ-nnn, PROP-nnn（Spec の節へのリンク）
**設計**: Design Spec の該当節、関連 ADR

## 受入条件
- [ ] <検証可能な条件>（REQ-nnn）

## 変更許可ファイルの範囲
- allow: `app/**`, `tests/**`
- deny: `tests/acceptance/**`（hold-out は holdout-test-writer だけが書く）

## 承認
<タスク定義を承認した人と日付（Phase 3 の品質ゲート）>
```

`/goal` が使える環境では、「G1〜G3 を通過する」をゴール条件に設定しておく。
別の評価器が毎ターン再判定するため、解決するまで作業が続く。

---

## Step 1: Hold-out Phase（受入テスト作成）

**`holdout-test-writer` サブエージェントに委譲する。**

- 入力: Spec の受入条件（UC-nnn）と Property（PROP-nnn）
- 出力: `tests/acceptance/` の受入テスト（受入条件1件につき最低1テスト）
- このテストは以降 **Green Phase から読めない**（Hook で拒否される）

コミット: `test(acceptance): [タスクID] hold-out 受入テスト - UC-nnn〜`

> このフェーズを飛ばすと、監督面が「Green が読めるテスト」だけになる。
> 可視のテストだけを通す実装（reward hacking）を検出できなくなるため、省略しない。

---

## Step 2: Red Phase（テスト作成）

**`red-agent` サブエージェントに委譲する。**

1. 受入条件からテストケースを設計する（正常系・異常系・境界値）
2. `PROP-nnn` があれば property-based test も書く
3. 各テストに `REQ-nnn` / `PROP-nnn` を書く（G2 のトレーサビリティ検証が走査する）
4. テストを実行し、**全て失敗する**ことを確認する
5. コミットする: `test: [タスクID] Red - [テスト内容の要約]`
6. **RED タグを打つ**:
   ```bash
   git tag jsix/red-<タスクID>
   ```

**RED タグは G2 のテスト改変検出の基準点**。打ち忘れると検出そのものがスキップされる。
タスクID は `JSIX_TASK_ID` 環境変数でも渡せる。

---

## Step 3: Green Phase（最小実装）

**`green-agent` サブエージェントに委譲する。**

1. テストが通る**最小限の**実装を書く
2. テストを実行し、**全て成功する**ことを確認する
3. コミットする: `feat: [タスクID] Green - [実装内容の要約]`

green-agent には Hook が付いており、`tests/` への書き込みと `tests/acceptance/` の
読み取りが機械的に拒否される。テストの期待値が誤っていると報告してきた場合は、
**テストを直す前に人間に判断を仰ぐ**（テスト・Spec・実装のどれが誤っているかは業務判断）。

---

## Step 4: Refactor Phase（リファクタリング）

**`refactor-agent` サブエージェントに委譲する。**

1. コードの品質を改善する（命名、構造、重複排除）
2. テストが**引き続き全て成功する**ことを確認する
3. 必要に応じてコミットする: `refactor: [タスクID] [改善内容]`

テストコードの整理も行ってよいが、**アサーション数・テスト関数数を減らさない／
無効化マーカーを増やさない**こと（G2 でブロックされる）。

---

## Step 5: 品質ゲート G1 → G4

```bash
# 内側ループ（ローカル）: 宣言された成果物を読んで判定する
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/jsix_run_checks.py"

# 成果物をまだ生成していない場合はコマンドも実行する
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/jsix_run_checks.py" --run-commands
```

終了コード0は設定・選択された検査についての結果であり、必須集合の充足やL4認定を単独では証明しない。2はいずれか未達。

### G1 / G2 が落ちた場合

出力に「どのチェックが、なぜ落ちたか」が出る。修正して再実行する。ただし
**テストを弱めて通してはいけない**。以下は即座に人間へエスカレーションする。

- テスト改変検出（`test_tamper`）でブロックされた
- 同じテストを3回続けて通せない
- Stop hook の連続ブロックが6回に達した（8回で自動解除されるため、その前に相談する）

### G3（意図・スコープ判定）

G1・G2 を通過すると、ランナーは「G3 未実施」で止まる。command 型 Hook から
LLM サブエージェントは呼べないため、ここは2段構成になっている。

1. **`scope-judge` サブエージェントを起動する**。渡すもの: diff / タスク定義 / 該当 Spec の節
2. scope-judge が判定を `reports/evidence/judge.json` に書き出す
3. ランナーを再実行する。ランナーが判定を読んで G3 を判定する

**REJECT された場合**:
- 1回目: 却下理由（`correctness` / `requirement` / `scope`）に従って修正し、再判定する
- 2回目: **人間に判断を仰ぐ**（`max_auto_fix` の既定は 1）

### G4（証跡パッケージ生成）

G3 を通過すると証跡パッケージが `reports/evidence/<タスクID>/` に生成される。
`evidence-pack` Skill で人間向けの要約を付加する。

---

## Step 6: ADR 記録（該当する場合）

実装中に以下の判断が発生した場合、ADR を記録する:
- ライブラリ・フレームワークの選択
- データ構造やアルゴリズムの選択（非自明な場合）
- パフォーマンスとのトレードオフ
- セキュリティに関わる判断

ADR テンプレート: `${CLAUDE_SKILL_DIR}/templates/adr-template.md`（Skill に同梱）

---

## エスカレーション条件

以下の場合はユーザーに判断を仰ぐ:

| 条件 | 理由 |
|---|---|
| 受入条件に曖昧さがある | 解釈の選択は業務判断 |
| 設計判断が必要（Spec に記載のない技術的判断） | 影響範囲の評価が必要 |
| テストが3回連続で失敗する | 根本的な設計問題の可能性 |
| **テスト改変検出でブロックされた** | 監督面を壊す操作であり、自動修正させてはならない |
| **G3 judge が2回目の却下をした** | 1回の修正で解決しない＝タスク定義側の問題の可能性 |
| **Stop hook の連続ブロックが6回に達した** | 8回で自動解除される。その前に判断を仰ぐ |
| セキュリティに関わる判断が必要 | リスク判断は人間の領域 |
| 外部インターフェースの変更が必要 | 他システムへの影響 |
| アーキテクチャの変更が必要 | CLAUDE.md で変更禁止のファイル等 |

---

## 完了条件

- [ ] hold-out 受入テストが `tests/acceptance/` に存在し、通っている
- [ ] 全受入条件・REQ・PROP に対応するテストが存在する
- [ ] 全テストが成功している
- [ ] RED タグ（`jsix/red-<タスクID>`）が打たれている
- [ ] 方針上の必須検査を満たす。L4はG1〜G4全層通過。G3省略構成はG1/G2/G4と省略方針を確認し最大L3とする
- [ ] コードが CLAUDE.md の規約に準拠している（G1 の lint / format で確認済み）
- [ ] 必要な ADR が記録されている
- [ ] コミット履歴が Hold-out → Red → Green → Refactor の流れを反映している
- [ ] 証跡パッケージが `reports/evidence/<タスクID>/` に生成されている
