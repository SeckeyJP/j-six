## エグゼクティブサマリー

J-SIX（Japanese SI Transformation）は、Anthropic Claude Code（以下CC）の能力を最大限に活用することを前提に再設計した、日本のSI業界向けシステム開発プロセスである。

従来のV字モデルに CC を「貼り付ける」のではなく、CC の能力を前提にプロセス自体を再構築した。世界標準の Spec-Driven Development（SDD）の原則を採用しつつ、日本特有の品質基準・設計書文化・受発注構造に対応する「日本品質レイヤー」を独自に設計している。

### 4つの設計原則

| # | 原則 | 内容 |
|---|---|---|
| 1 | **CC ネイティブ** | 外部フレームワーク（BMAD等）に依存せず、CC のネイティブ機能のみで構築 |
| 2 | **3層ドキュメント** | Spec（Why）+ ADR（Why Not）+ 逆生成設計書（What/How）で従来設計書を超越 |
| 3 | **TDD が品質の中核** | テストファーストにより CC 自律実行の品質を担保 |
| 4 | **段階的移行** | 既存V字モデルから3ステージで移行。既存案件を止めない |

### 期待効果

|---|---|---|---|---|

## 第1章：なぜ従来プロセスを再設計するのか

### 1.1 V字モデルの前提崩壊

V字モデルは「実装コストが高く、変更が困難」な時代に最適化されたプロセスである。CC により以下の前提が崩壊した。

| 崩壊した前提 | CC がもたらす現実 |
|---|---|
| 実装コストが高い | CC は数分で数百行のコードを生成する |
| 人間が全行コードを書く | CC が大部分を生成し、人間はレビュー・判断に集中 |
| テスト作成が高コスト | テストコードを自動生成。TDD サイクルが CC 前提で回る |
| 変更が困難 | 変更コストが劇的に低下。リファクタリングも CC 任せ |

### 1.2 しかし変わらないもの

| 変わらない前提 | 理由 |
|---|---|
| 何を作るかの合意は人間が行う | ビジネス要件・ステークホルダー合意は AI で代替不可 |
| アーキテクチャ判断は人間が行う | 技術選定・非機能要件のトレードオフは文脈依存 |
| 品質の最終責任は人間にある | CC 生成コードには人間より多いロジックエラーを含む報告あり |
| トレーサビリティは必要 | 監査・保守において要件→実装→テストの追跡可能性は不可欠 |
| 顧客との合意プロセスは必要 | 日本のSIモデルでは受発注関係がある |

### 1.3 CC の現実的な能力水準

> **注**: 以下のデータは各出典の発表時点のものである。モデルの世代更新（Sonnet 4.5 → Opus 4.6 → Opus 4.7 等）により能力水準は継続的に改善されている。最新のベンチマークは各出典元を参照のこと。

| 指標 | 数値 | 出典 | データ時点 |
|---|---|---|---|
| 人間の介入頻度の変化 | 33%減少（6.2→4.1ターン/タスク） | Anthropic 社内調査 [3] | 2025 |
| AI生成PRのイシュー率 | 人間の約1.7倍（10.83 vs 6.45件/PR） | CodeRabbit 調査（470PR分析）[8] | 2025.12 |
| セキュリティイシュー | 人間の最大2.74倍 | 同上 [8] | 2025.12 |
| コード編集エラー率 | 9%→0%（Sonnet 4→4.5） | Replit 内部ベンチマーク [4] | 2025.09 |
| CC の連続自律アクション数 | 約10→約20（6ヶ月で2倍） | Anthropic 社内調査 [3] | 2025 |

**含意**: CC は高速だが、人間より多くのイシューを含むコードを生成する傾向がある。適切なガードレール（TDD + Hooks + レビュー）があれば実用水準だが、「任せっきり」は危険。モデル世代の進化により自律実行能力は急速に向上している。

### 2.2 従来V字モデルとの本質的な違い

| 観点 | V字モデル（従来） | J-SIX |
|---|---|---|
| **Source of Truth** | 設計書（Excel/Word） | Spec + コード + テスト（三位一体） |
| **設計書の位置づけ** | 実装前に書く「設計図」 | 実装後にコードから逆生成する「納品物」 |
| **実装者** | 人間（SE/PG） | CC 自律実行（TDD サイクル） |
| **品質保証** | レビュー会議 + テスト | TDD + CC相互レビュー + 人間サンプリング |
| **テストの位置づけ** | 実装後に書く | **実装前に書く（TDD）** |
| **並列性** | 基本的に直列 | **Agent Teams + git worktree で大規模並列** |
| **変更耐性** | 低い（凍結管理） | **高い（TDD + 自動リグレッション）** |

### 2.3 自律度の5段階モデル

```
L0: 手動          人間が全て実行、CC は参考回答のみ
L1: CC 支援       人間が主導、CC が補助
L2: CC 主導       CC が実行案を作成、人間が毎回承認
L3: CC 自律       CC が自律実行、人間は結果を監督・異常時介入
L4: CC 完全自律   CC が自律実行、人間は介入しない
                  （条件: Phase 4 の G1〜G4 全層通過。自動テストのみでは L4 に到達しない）
```

**基本原則**: 判断（What/Why）は人間、実行（How）は CC。影響範囲が大きいほど人間の関与を増やす。

#### L4 の条件を「自動テスト通過」から「G1〜G4 全層通過」に改めた理由

v2.0 では L4 を「人間は介入しない（自動テストのみ）」と定義していた。これは**最も脆弱な構成**である。
エージェントにとって唯一の監督面がテストスイートであるとき、テストスイートは検証手段ではなく
**最適化対象**になる。結果として「テストは通るが意図を満たさない実装」が生じる（reward hacking）。

SpecBench は、可視の検証テストと hold-out テストの pass 率の差でこの現象を定量化し、
フロンティアモデルはいずれも可視テストを飽和させる一方で hold-out との差は残ること、
そしてその差はテストの網羅度ではなく**タスク難度とモデル能力の差**で拡大することを報告している [26]。
「カバレッジを上げれば防げる」という素朴な対策が効かないことを意味する。

したがって L4 の条件は、テストスイート単独ではなく、**性質の異なる複数の監督面**
（決定論的検証 / エージェントが書けないテスト / 別コンテキストの判定 / 証跡）を
すべて通過することとする。具体的な4層は Phase 4 に定義する。

## 第3章：各 Phase の詳細

### Phase 0: プロジェクト憲法策定（CLAUDE.md）

**自律度**: L1（人間が主導、CC が支援）
**従来の対応物**: 開発標準、コーディング規約、プロジェクト計画書

CLAUDE.md はプロジェクトの全ルールを CC が理解・実行可能な形式で記述した「憲法」。CC の全出力がこの文書に制約される。Anthropic 社内の調査でも「CLAUDE.md の充実度と CC 出力品質は直接相関する」と報告されている [2][19]。

**CLAUDE.md に定義すべき内容**:

```
CLAUDE.md
├── プロジェクト概要
│   ├── システムの目的・業務概要
│   ├── アーキテクチャ方針
│   └── 技術スタック
├── 開発規約
│   ├── コーディング規約（命名規則、フォーマット）
│   ├── ディレクトリ構成ルール
│   ├── Git 運用ルール（ブランチ戦略、コミットメッセージ）
│   └── エラーハンドリング方針
├── 設計方針
│   ├── DB 設計ルール
│   ├── API 設計ルール
│   └── 画面設計ルール
├── 品質基準
│   ├── テストカバレッジ目標
│   ├── 静的解析ルール
│   └── パフォーマンス基準
├── ADR ルール
│   ├── ADR 必須の判断基準
│   └── ADR テンプレートの場所
└── 禁止事項・制約
    ├── 使用禁止ライブラリ
    ├── セキュリティ制約
    ├── 変更禁止ファイル一覧
    └── 本番環境に関する制約
```

#### CLAUDE.md をコードとして扱う（継続運用）

CLAUDE.md は Phase 0 で書いて終わる文書ではない。**品質ゲートの失敗理由と人間レビューの指摘**が、
そのプロジェクトで CC が繰り返す誤りの実測データである。これを毎月 CLAUDE.md / Hook / Skill に
還元する。

| 観測されたもの | 還元先 | 理由 |
|---|---|---|
| 同じ規約違反が繰り返される | CLAUDE.md の該当行を強調、または **Hook 化** | 助言（CLAUDE.md）は守られないことがあるが、Hook は決定論的に効く |
| ゲート G1 の同じチェックが何度も落ちる | 編集後（PostToolUse）の format/lint Hook | 落ちてから直すのではなく、書いた時点で直す |
| 人間レビューで同種の指摘が続く | Skill（手順の明文化） | 都度の指示ではなく再利用可能な手順にする |
| 特定の判断で毎回エスカレーションが起きる | CLAUDE.md の判断基準を追記 | 判断基準が言語化されていないサイン |

公式ガイドは CLAUDE.md について「肥大化すると重要なルールが埋もれて無視される」と警告しており [1]、
**足すだけでなく削る**こと、および「CC が指示なしでも正しくできることは消すか Hook に変換する」ことを
月次ループに含める。

### Phase 1: 要求の合意

**自律度**: L1-L2（人間が主導、CC がドラフト生成・曖昧性検出）
**従来の対応物**: 要件定義工程
**成果物**: 要求 Spec（3層戦略の第1層）

**フロー**:
1. ステークホルダーヒアリング（人間）
2. CC インタビューモード：曖昧性の発見・深掘り質問の自動生成
3. CC による並列リサーチ（Subagents で業務ドメイン・技術動向を調査）
4. 要求 Spec 作成（CC がドラフト生成 → 人間がレビュー）。非機能要件は IPA「非機能要求グレード」の
   6大項目（可用性 / 性能・拡張性 / 運用・保守性 / 移行性 / セキュリティ / システム環境・エコロジー）で分類する [34]
5. 業務フロープロトタイプ生成（CC が即時生成 → 顧客確認）
6. 🚪 品質ゲート: 顧客承認（合意対象が**完成レベル**にあること。下記）

**CC 機能**: Plan Mode, ask_user_question, Subagents（並列リサーチ）

#### 合意成熟度による判定（Phase 1・2・6 の品質ゲート）

顧客と合意するゲートでは、「レビューした」ではなく**合意がどの段階まで進んだか**で判定する。
段階は IPA「機能要件の合意形成ガイド」の合意成熟度の3レベルを用いる [32]。

| レベル | 定義（IPA ガイド 3.1.1） |
|---|---|
| 仕掛レベル | 発注者が「言い切った」、開発者が「聞き切った」 |
| 充実レベル | 図表に書いてレビューを繰り返し、合意内容が充実した |
| 完成レベル | 合意内容が管理され、発注者・開発者の双方が確認できた |

成熟度は**合意対象ごと**に判定する。J-SIX では設計書の多くを実装から逆生成するため、
同じ Phase 2 のゲートでも、人手で書く成果物は完成レベル、逆生成する成果物はプロトタイプ等の
代替物による充実レベルまでしか到達しない。これを「未達」と扱わず、ゲートごとの到達基準を
次のように定める。

| ゲート | 完成レベルを求める合意対象 | 充実レベルでよい合意対象 |
|---|---|---|
| Phase 1 顧客承認 | 要求 Spec（ユースケース・業務ルール REQ・受入条件と PROP・非機能要件） | 業務フロー（プロトタイプで確認） |
| Phase 2 設計レビュー | Design Spec・ADR・実動プロトタイプ、人手で書く工程成果物、提出する設計書の目次（組立定義） | 実装から逆生成する工程成果物（代替物で確認し、Phase 6 で差し替える） |
| Phase 6 納品物レビュー | 逆生成した工程成果物を含む全納品物 | — |

判定の観点は各テンプレートの「承認」欄にチェックリストとして置いている
（`templates/spec/requirement-spec.md`・`design-spec.md`）。仕掛レベルの項目が残っている場合は、
「未確定」と明記したうえで確定させる Phase と担当者を決めない限りゲートを通さない。

### Phase 2: 技術設計

**自律度**: L2（人間がアーキテクチャ判断、CC が具現化）
**従来の対応物**: 基本設計工程
**成果物**: Design Spec + 実動プロトタイプ + ADR（3層戦略の第1層・第2層）

**フロー**:
1. アーキテクチャ決定（人間が判断）→ ADR に記録
2. Design Spec 作成
   - DB 設計 → DDL → ER図 を一貫生成（CC）
   - API 設計 → OpenAPI Spec 自動生成（CC）
   - 画面設計 → 実動 HTML プロトタイプ生成（CC）
3. 技術選定の裏付け調査（CC Subagents が並列実行）→ ADR に記録
4. **受入条件から Property（PROP-nnn）を導出**（下記）
5. 🚪 品質ゲート: 設計レビュー（プロトタイプベースのレビュー。合意成熟度の到達基準は Phase 1 の表）

#### 受入条件 → Property（PROP-nnn）の導出

受入条件は「この入力ならこの出力」という**個別の例**で書かれることが多い。例だけを検証面にすると、
エージェントはその例だけを通す実装に最適化できてしまう。そこで受入条件から、入力空間全体で
成り立つべき**性質**を取り出し、`PROP-nnn` として Spec に記録する。

書式は「**任意の〈前提〉について〈性質〉が成り立つ**」で統一する。

| 元の受入条件（例） | 導出した Property |
|---|---|
| 10万円の申請は2段承認になる | PROP-001: 任意の金額について、必要承認段数は金額の単調非減少関数である |
| 申請者は自分の承認者になれない | PROP-002: 任意の申請について、承認者リストに申請者は含まれない |
| 承認は順序どおりに行う | PROP-003: 任意の操作列について、監査ログの件数は状態遷移の回数と一致する |

Property は Phase 4 で property-based testing（PBT）のテストに変換する。この
「仕様 → 性質 → PBT」の流れは Kiro が実装している方式に倣ったものである [28][29]。
PROP は REQ と同じくトレーサビリティ・キーとして扱い、テストコードに ID を書く。

**レビューの革新**: 「紙の設計書」ではなく「動くプロトタイプ」でレビュー。「設計書には書いてあるが動かない」問題を根絶。

**CC 機能**: Plan Mode, Subagents（並列調査）, CLAUDE.md（設計方針の永続化）

### Phase 3: タスク分解

**自律度**: L2（CC がタスク提案、人間が承認）
**従来の対応物**: 詳細設計工程 + WBS 作成
**成果物**: タスク一覧（受入条件付き）

**フロー**:
1. Design Spec → タスク自動分解（CC）
2. 各タスクに受入条件（テスト条件）と対応する **PROP-nnn** を定義（CC）
3. 各タスクに**変更許可ファイルの範囲**（allow / deny）を定義（CC 提案 → 人間承認）
4. 依存関係・並列実行可能性の分析（CC）
5. 🚪 品質ゲート: タスク承認（自律実行圏への最後のゲート）

**変更許可ファイル範囲を Phase 3 で決める理由**: Phase 4 の G1 スコープ検査は
「変更ファイル ⊆ タスクの許可リスト」を機械的に判定する。この許可リストは自律実行が
始まる前に人間が承認しておく必要がある（実行中に CC 自身が広げられるなら検査の意味がない）。

**Phase 3 の完了 = CC 自律実行の開始**。ここまでの上流工程で「何を作るか」「どう作るか」「どう検証するか」が全て定義される。

**CC 機能**: Native Tasks システム

### Phase 4: TDD 実装 ★生産性の源泉

**自律度**: L3-L4（CC が自律実行、人間は監督・異常時介入）
**従来の対応物**: 実装 + 単体テスト

**J-SIX の最も革新的な Phase**。3つのメカニズムで品質を担保しつつ、CC の自律実行で最大の生産性を発揮する。

#### メカニズム①: TDD サイクル（サブエージェント分離）

```
🟣 HOLD-OUT: 受入テスト作成（CC サブエージェント D）
   ↓       tests/acceptance/ にコミット。以降 GREEN は読めない
🔴 RED:    テスト作成（CC サブエージェント A。PROP は PBT として生成）
   ↓       テスト失敗を確認 → テストをコミット【チェックポイント】
   ↓       git tag jsix/red-<task-id>  ← G2 テスト改変検出の基準点
🟢 GREEN:  最小実装（CC サブエージェント B）
   ↓       テスト通過を確認 → 実装をコミット【チェックポイント】
🔵 REFACTOR: リファクタリング（CC サブエージェント C）
   ↓       テスト通過を再確認 → コミット
   ↓       G1 → G2 → G3 → G4

※ サブエージェント分離 = コンテキスト汚染の防止 [14]
※ テストをコミットしてから実装にハンドオフ = テスト改変の防止 [1][16]
※ hold-out は別サブエージェントが別コンテキストで書き、GREEN からは読取禁止 = 監督面の分離 [26]
```

**hold-out 受入テストの規模**: 受入条件（UC-nnn）1件につき最低1テスト。GREEN が参照できない
テストを残すことで、「見えているテストだけを通す実装」を検出できる。

#### メカニズム②: 順序固定の4層品質ゲート

人間レビューに出す前に、**性質の異なる4つの監督面**を順に通す。順序は固定で、
**後段は前段を通過した場合のみ実行する**。壊れたコードを LLM judge に見せないためである。
Spotify が数千のエージェントセッションを運用した Honk でも、決定論的検証器
（format / build / test）をすべて通してから LLM judge を走らせる順序を採っている [27]。

| 層 | 名称 | 内容 | 判定主体 |
|---|---|---|---|
| **G1** | 決定論的検証 | build / 型 / lint・format / SAST / secret scan / 依存脆弱性 / **スコープ検査**（変更ファイル ⊆ タスクの許可リスト） | script（終了コード） |
| **G2** | テスト品質検証 | 全テスト通過（JUnit）/ カバレッジ閾値 / **mutation score** / **テスト改変検出** / **hold-out 受入テスト**通過 / トレーサビリティ（REQ・PROP ⇔ テスト） | script（終了コード） |
| **G3** | 意図・スコープ判定 | diff ＋ タスク ＋ Spec を fresh context の judge に渡し、**正確性・要件未充足・スコープ逸脱の3点のみ**を報告 | LLM（scope-judge サブエージェント） |
| **G4** | 証跡パッケージ生成 | G1〜G3 の結果を人間レビュー用・顧客納品用に構造化（第9章） | script ＋ LLM（要約部のみ） |

**各層が防ぐもの**:

- **G1** は「動かないもの・危ないもの・頼んでいないファイルを触ったもの」を落とす。LLM を介さないため判定がぶれない。
- **G2** は「テストが通ること」ではなく「**テストが機能していること**」を検証する。カバレッジは
  テストが通った行を数えるだけなので、mutation score（コードを意図的に壊してテストが落ちるか）と、
  **エージェントが書いていないテスト**（hold-out）を併用する。
- **G3** は G1・G2 が原理的に見られないもの——「動くし、テストも通るが、頼んだものと違う」——だけを見る。
- **G4** は判定の根拠を残す。日本の SI では「品質が良い」ことと「品質が良いと示せる」ことは別の要件である。

##### G2 の「テスト改変検出」

TDD の RED 完了時点に `jsix/red-<task-id>` タグを打ち、それ以降の `tests/` の差分を検査する。
検出対象は**テストを弱める変更**である。

| 検出パターン | 判定 |
|---|---|
| assert / expect の削除 | ブロック |
| `skip` / `xfail` 等の無効化マーカーの追加 | ブロック |
| テスト関数の減少 | ブロック |
| 実装コードから hold-out テストへの参照 | ブロック |
| 上記以外の `tests/` の差分（命名整理・重複排除等） | 証跡に記録して警告（REFACTOR 工程を止めない） |

**Writer/Reviewer パターン**（コードを書いた CC とは別インスタンスがレビューする）は
G3 に統合された。自分が書いたコードへのバイアスを排除するという目的は変わらない。

##### G3 に「スタイル指摘の禁止」を明記する理由

公式ガイドは、gap を探せと指示されたレビュアーは**作業が健全でも何かを報告する**傾向があり、
その指摘を全部追うと過剰な抽象化・防御的コード・起こり得ないケースのテストを生むと警告している [1]。
そこで G3 の judge には、正確性・要件未充足・スコープ逸脱の3分類**以外**の指摘（スタイル、
命名の好み、将来の拡張性）を禁止する。

##### G3 は固定装備ではない

Spotify は Honk の初期に LLM judge を導入して大きな効果を得たが、その後**モデルの改善に伴い
judge を撤去**している（判定が硬直的で妥当な変更まで止めたため）[30]。J-SIX でも G3 は恒久的な
装備とはみなさず、**却下率と却下理由の分布をメトリクスとして計測し**（Phase 5）、却下がほぼ
起きなくなった、あるいは誤った却下が増えた時点で外す判断を行う。G1・G2・G4 は決定論的で
コストが低いため、この判断の対象外とする。

#### メカニズム③: 並列実行

```
タスク A ─── [TDD サイクル] → [Review] → ✅
タスク B ─── [TDD サイクル] → [Review] → ✅  ← git worktree で並列
タスク C ─── [TDD サイクル] → [Review] → ✅  ← Agent Teams で協調
タスク D ─── [待機: A に依存] → 開始 → ...
```

#### エスカレーション条件（CC → 人間）

以下の場合、CC は自律実行を中断し人間に判断を仰ぐ。

| 条件 | 理由 | 実装 |
|---|---|---|
| Spec に記載のない要件が必要 | 業務判断は人間の領域 | ask_user_question |
| セキュリティに関わる判断 | リスク判断は人間が行うべき | Hook で検出 |
| 外部 IF 仕様の変更が必要 | 他システムへの影響 | Hook で検出 |
| テスト3回連続失敗 | 根本的な設計問題の可能性 | Hook で監視 |
| アーキテクチャ変更が必要 | 影響範囲大 | CLAUDE.md で変更禁止ファイル定義 |
| **テストを弱める変更を試みた**（skip / xfail 追加、assert 削除、SUT のモック化、hold-out の参照） | 監督面そのものを壊す操作であり、自動修正させてはならない | G2 テスト改変検出で即時ブロック＋人間へ通知 |
| **G3 judge が「スコープ逸脱」で却下** | 頼んでいない変更が入っている | 修正1回までは自動、2回目で人間へ |
| **Stop hook の連続ブロックが上限に近づいた** | Hook は最終防衛線ではない | 同じ失敗が3回続いたら停止を許可し未達のまま残す（CI で止める）。失敗が変化しながら6回に達したら人間へ通知（下記） |

**Stop hook の連続ブロック上限**: CC は Stop hook が **進捗の無いまま8回連続でブロックすると hook を
上書きしてターンを終了する** [1]。つまり Hook は「絶対に止まる壁」ではない。J-SIX では6回目で人間に
通知し、8回目の自動解除に到達する前に判断を仰ぐ。あわせて、Hook が解除されても止まるように
**外側ループ（CI）** を併設する（第4章 4.4）。

**工程上いま満たせない失敗**: Spec に REQ を追加した直後（テストは Phase 4 で書く）のように、ゲートが
その工程では満たせない失敗を返すことがある。偽のテストで通すのは結果の偽装であり、してはならない。
一方で Stop のたびに同じ失敗でブロックし続けると、セッションが終わらない（Skill のヘッドレス実行で
15回繰り返した）。そこで品質ゲートのランナーは、Stop hook として呼ばれたときに限り、**失敗内容が
変わらないブロックが3回続いたら停止を許可する**（`.jsix-checks.json` の
`stop_hook.max_identical_blocks` で変更可）。判定は緩めず、ゲートは未達のまま残り、CI では止まる。

**CC 機能**: Subagents（TDD 分離 / scope-judge）, Agent Teams（並列実行）, git worktree, Hooks（Stop / PostToolUse）, チェックポイント, `/goal`（G1〜G3 通過を goal 条件に設定）, `/code-review`

### Phase 5: 品質検証

**自律度**: L2-L3（自動チェック + 人間サンプリング検証）
**従来の対応物**: 結合テスト + 総合テスト + 品質管理

> **v2.1 での役割整理**: カバレッジ計測・静的解析・Spec⇔コード整合性は Phase 4 の G1/G2 に
> 移した（タスク単位で毎回実行する方が、Phase 5 でまとめて実行するより早く安く直せる）。
> Phase 5 は **G1〜G4 を通過した成果物に対して、機械が原理的に見られないものを人間が見る工程**
> として再定義する。

**フロー**:
1. 証跡パッケージのレビュー（人間）
   - Phase 4 の G4 出力（第9章）を読み、決定論的な**証跡**と AI による**参考所見**を区別して確認
   - 参考所見（G3 judge の判定・LLM 要約）を単独で品質判定の根拠にしない
2. 人間による検証
   - CC コードレビュー結果のサンプリング検証
   - 設計判断・業務ロジックの妥当性確認
   - 探索的テスト（人間の直感によるテスト）
3. 結合・E2E テストの実行（タスク単位の G1/G2 では見えない、モジュール間の結線を検証）
4. 品質メトリクスの集計（下記）
5. 🚪 品質ゲート: 品質基準達成判定

**Phase 5 で集計するメトリクス**:

| メトリクス | 用途 |
|---|---|
| mutation score（全体 / 変更範囲） | テストスイート自体の有効性 |
| G3 judge の却下率と却下理由の分布 | judge を継続するか外すかの判断材料（Phase 4 参照） |
| ゲート失敗理由の分布 | CLAUDE.md / Hook / Skill への還元先の特定（Phase 0 の月次ループ） |
| 人間レビュー指摘数 / PR | ゲートが機能しているかの外形指標。ゲート強化に伴い減るはず |

**品質基準は従来と同等を維持**: バグ密度、カバレッジ率等の定量基準は変えない。自動化により網羅性はむしろ向上。

**検証コストは消えるのではなく移動する**: DORA は、AI 導入により「コードを書く時間は減るが、
AI の作業を見張りレビューする時間が増える」という開発者の声、および**開発者の30%が AI 生成
コードをほとんど信頼していない**ことを報告している [31]。J-SIX の4層ゲートは、この検証負荷を
人間のレビュー時間から機械的な検証（G1・G2）と証跡（G4）へ移すことを狙うものであり、
検証そのものを不要にする主張ではない。

### Phase 6: ドキュメント生成（3層戦略）

**自律度**: L3（CC が自動生成、人間がレビュー・承認）
**従来の対応物**: 各工程で作成していた設計書を一括生成

**J-SIX 最大のパラダイムシフト**: 設計書は「事前に書くもの」から「事後に生成するもの」へ。

#### 3層ドキュメント戦略

```
┌────────────────────────────────────────────────────────┐
│ 第1層：Spec（Phase 1-2 で作成済み）                     │
│   「なぜ作るか」「何を作るか」                          │
│   ・要求 Spec（業務背景・目的・スコープ・制約）         │
│   ・Design Spec（アーキテクチャ方針・技術選定理由）     │
├────────────────────────────────────────────────────────┤
│ 第2層：ADR（Phase 2-4 で随時記録済み）                  │
│   「なぜそう判断したか」「他の選択肢は何だったか」       │
│   ・設計判断とその理由                                  │
│   ・検討した代替案と却下理由                            │
│   ・前提条件・制約の根拠                                │
├────────────────────────────────────────────────────────┤
│ 第3層：逆生成設計書（Phase 6 で自動生成）               │
│   「何をどう実装したか」                                │
│   ・工程成果物27点（IPA 合意形成ガイド準拠）            │
│   　→ 組立定義で基本設計書・詳細設計書等に束ねる        │
│   ・テスト仕様書・テスト結果                            │
│   ・ADR の内容を「設計根拠」欄に自動統合                │
└────────────────────────────────────────────────────────┘
```

#### なぜ3層が従来の設計書より優れるか

| 情報カテゴリ | 従来V字モデル | J-SIX（3層戦略） |
|---|---|---|
| 構造情報（What/How） | ○（設計書に記載） | ◎（コードから正確に逆生成） |
| 業務背景（Why Business） | △（形骸化しがち） | ◎（Spec で記録） |
| 設計判断理由（Why Technical） | △（暗黙知に留まる） | ◎（ADR で記録） |
| 却下した代替案（Why Not） | ×（記録されない） | ◎（ADR で記録） |
| 設計書⇔コードの整合性 | △（乖離が頻発） | ◎（原理的に一致） |
| トレーサビリティ | ○（手動管理） | ◎（自動リンク） |

🚪 品質ゲート: 納品物レビュー（従来フォーマットでの出力も対応）。逆生成した工程成果物を含む全納品物が
完成レベルに達したことをもって、Phase 2 で充実レベルに留めた合意対象を閉じる（Phase 1 の表）

### 4.2 CC 機能の Phase 別マッピング

**Plugin は言語別ツールを直接呼ばない**。`.jsix-checks.json` が「コマンド」と
「成果物のパス・形式」を宣言し、Plugin は標準フォーマット（JUnit XML / Cobertura・LCOV /
SARIF / mutation-testing-elements JSON）の**パースと閾値判定のみ**を行う。
これにより、特定言語のツール名を Plugin に持ち込まずに済む。

テンプレート（CLAUDE.md / Spec / ADR / 工程成果物）はリポジトリルートの `templates/` に配置し、Skills から参照する構成としている。
`templates/deliverables/` は IPA「機能要件の合意形成ガイド」が想定する工程成果物27点の
テンプレートであり、うち19点は Phase 6 でコードまたは受入テストから逆生成する。
工程成果物と顧客様式の設計書は1対1ではないため、束ね方（基本設計書・詳細設計書の組立例）を
`templates/deliverables/assembly/` に定義している。

### 4.4 内側ループ（Hook）と外側ループ（CI）の二重化

品質ゲートは**内側と外側の二重**で構成することを標準とする。

```
内側ループ（Hook / ローカル）        外側ループ（CI / リモート）
  Stop hook → G1 → G2 → G3 → G4       PR → G1 → G2 → G4
  速い。書いた直後に落ちる            遅い。しかし解除できない
        │                                    │
        └──── 同じスクリプト・同じ設定ファイル ────┘
```

**なぜ二重にするのか**: Hook は最終防衛線にならない。理由は3つある。

1. **8回で自動解除される**: Stop hook が進捗の無いまま連続8回ブロックすると、CC は hook を上書きしてターンを終了する [1]。
2. **ローカル設定である**: `.claude/settings.json` や plugin の有効化は各開発者の環境に依存する。
3. **オプトインである**: J-SIX の Plugin は `.jsix-checks.json` が無いプロジェクトでは何もしない（安全側の既定）。

したがって「Hook が解除されても CI ゲートで止まる」構成を標準とする。両者は**同じ判定スクリプトと
同じ設定ファイル**を使い、ローカルで緑になったものが CI で赤になる（またはその逆）ことを避ける。

**内側と外側の役割分担**:

| | 内側ループ（Hook） | 外側ループ（CI） |
|---|---|---|
| 目的 | 早く気づく | 確実に止める |
| 実行タイミング | ターン終了時 | PR / push |
| 既定の動作 | 宣言された成果物（JUnit / カバレッジ / SARIF 等）を**読んで判定する**。ビルドやテストのコマンド自体は実行しない | コマンドを実行して成果物を生成してから判定する |
| G3（LLM judge） | 実行する | 必須にしない（PR 上の `/code-review` に委ねてもよい） |

内側ループで長時間のコマンド（ビルド・mutation testing）を毎ターン走らせない設計としているのは、
Stop のたびに数分待たされると Hook 自体が無効化される運用に傾くためである。

## 第6章：日本特有の課題への対応

### 6.1 設計書文化

**対策**: Phase 6 でコードから設計書を逆生成。フォーマットは従来互換（Excel/Word）。コードが Source of Truth のため乖離が原理的に発生しない。

### 6.2 受発注・多重下請け構造

**対策**: CLAUDE.md により全参加者のルールを統一。Plugin として共有することで、下請け各社でも同一品質を確保。

### 6.3 品質保証部門（QA）

**対策**: QA の役割を「テスト戦略策定 + サンプリング検証 + 探索的テスト」に再定義。テスト実行の自動化によりQAは本質的な品質活動に集中。

### 6.4 IPA/共通フレーム・PMBOK

**対策**: J-SIX の Phase は共通フレームのアクティビティにマッピング可能。Phase 6 の設計書により監査証跡も従来互換で提供。

### 6.5 顧客が事前設計書を求める場合

**段階的対策**:
1. **短期**: Design Spec + プロトタイプを「基本設計書相当」として提出
2. **中期**: Spec + プロトタイプ + ADR を設計書の代替として合意
3. **長期**: 業界全体で「Spec + コード + テスト + ADR = 設計書」の認識を普及

短期策を章単位でどう運用するか（どの章を事前に出せ、どの章を納品時に逆生成版へ差し替えるか）は
`templates/deliverables/assembly/GUIDE.md` の「提出の時期は2回ある」と、基本設計書の組立例
（同 `kihon-sekkei.md`）の「事前提出」列に定義している。

## 第9章：証跡パッケージ（品質の証明と納品）

日本の SI では「品質が良い」ことと「品質が良いと**示せる**」ことは別の要件である。
Phase 4 の G4 は、G1〜G3 の結果を人間レビュー用・顧客納品用に構造化して出力する。

### 9.1 3つの区分を混ぜない

証跡パッケージの最大の設計原則は、**性質の違うものを同じ重みで並べない**ことである。

| 区分 | 内容 | 納品時の扱い |
|---|---|---|
| **証跡（Evidence）** | 決定論的検証の生出力と集計: JUnit / カバレッジ / mutation / SARIF / トレーサビリティ / スコープ検査 / テスト改変検出 | 納品可。**再現情報**（commit SHA・ツール名と版・実行日時・設定ファイルのハッシュ）を必ず添付する |
| **参考所見（Advisory）** | G3 judge の判定・LLM 要約・探索的テストの観点 | 「AI による参考所見」と明記する。**単独で品質判定の根拠にしない** |
| **承認（Approval）** | 人間レビュアーの確認欄・指摘事項・是正記録 | 必須。承認者と日付を記録する |

参考所見を証跡と区別する理由は単純で、LLM の判定は再実行しても同じ結果になるとは限らず、
第三者が同じ手順で確かめられないためである。証跡は誰が何度実行しても同じ値になる。

### 9.2 構成（`reports/evidence/<task-id>/`）

```
evidence.json             機械可読の全結果（後工程・ダッシュボード用）
00_summary.md             1ページ要約（変更概要・ゲート結果一覧・リスク箇所・計画からの逸脱）
01_traceability.md        REQ / PROP ⇔ テスト ⇔ コード の対応表
02_test_results.md        テスト結果（件数・失敗・スキップ）＋ hold-out 結果
03_coverage_mutation.md   カバレッジと mutation score（変更範囲 / 全体）
04_security.md            SARIF 集計（severity 別件数、未対応の理由）
05_scope_and_integrity.md スコープ検査・テスト改変検出の結果
06_judge_advisory.md      G3 judge の判定と理由（参考所見）
07_approval.md            人間レビュー記録（承認欄）
env.json                  commit SHA / ツール名と版 / 実行日時 / 設定ハッシュ
```

`00_summary.md` の LLM 要約部分は「参考所見」として明示的に囲む。要約が誤っていても、
その下の 01〜05 の数値は独立に検証できる構造にしている。

### 9.3 従来納品物への対応付け

Phase 6 の `doc-reverse-gen` Skill が、証跡パッケージを従来フォーマット（Excel / Word）に変換する。

| 従来納品物 | 証跡パックの元データ |
|---|---|
| 単体テスト仕様書・テスト結果報告書 | 01, 02 |
| 品質報告書（品質メトリクス） | 03, 05 ＋ Phase 5 の集計 |
| セキュリティ診断結果 | 04 |
| トレーサビリティマトリクス | 01 |
| レビュー記録 | 06（参考所見）, 07（承認） |

**従来との違い**: これらは「納品直前に人手で作る文書」ではなく、**Phase 4 でタスクごとに
自動生成された記録の集積**である。作成コストがほぼゼロになる一方、記載内容は実行時の
実データであるため、コードとの乖離が原理的に起こらない。

### C. 用語集

| 用語 | 定義 |
|---|---|
| CC | Claude Code（Anthropic のエージェント型コーディングツール） |
| J-SIX | Japanese SI Transformation。本ドキュメントで提案する CC フル活用・AI ネイティブ開発プロセス |
| SDD | Spec-Driven Development（仕様駆動開発） |
| ADR | Architecture Decision Records（アーキテクチャ判断記録） |
| TDD | Test-Driven Development（テスト駆動開発） |
| Phase Gate | 工程完了時の品質判定・承認ポイント |
| CLAUDE.md | CC のプロジェクト設定ファイル（プロジェクト憲法） |
| Spec | 仕様書（要求 Spec / Design Spec） |
| L0-L4 | CC の自律度レベル（0=手動、4=完全自律） |
| 逆生成 | 実装済みコードから設計書を自動生成すること |
| 3層戦略 | Spec + ADR + 逆生成設計書 による文書体系 |
| G1-G4 | Phase 4 の順序固定4層品質ゲート（決定論的検証 / テスト品質検証 / 意図・スコープ判定 / 証跡生成） |
| PROP | Property。「任意の〈前提〉について〈性質〉が成り立つ」形式で書いた検証可能な性質。ID は `PROP-nnn` |
| PBT | Property-Based Testing。入力を自動生成して Property が破れないかを試すテスト手法 |
| 工程成果物 | 設計書を構成する単位の成果物。J-SIX では IPA 機能要件の合意形成ガイドの27点を用いる |
| 組立定義 | 顧客様式の設計書の章と、それを構成する工程成果物・Spec・ADR の対応表 |
| 合意成熟度 | 合意がどこまで進んだかの3段階（仕掛／充実／完成レベル）。Phase 1・2・6 の品質ゲートの到達基準に使う |
| 非機能要求グレード | IPA が非機能要求を6大項目・238メトリクスに体系化したもの。要求 Spec の非機能要件の分類に使う |
| mutation score | コードを意図的に改変（ミュータント生成）し、テストが失敗した割合。テストスイート自体の有効性を測る |
| hold-out テスト | 実装を書くエージェントが読めない受入テスト。可視テストへの過剰適合を検出する |
| reward hacking | 監督面（テスト等）を最適化対象として扱い、意図ではなく指標を満たしにいく挙動 |
| 証跡パッケージ | G4 が出力する、決定論的検証の生出力と集計をまとめた納品可能な記録一式 |
| 内側/外側ループ | 内側=ローカルの Hook による早期検知、外側=CI による確実な遮断 |

### E. 本ドキュメントの性質について

J-SIX は著者が設計したオリジナルの開発プロセス提案であり、上記参考文献の知見を統合・再構成したものである。具体的には以下の通り。

- **J-SIX の7Phase 構成、3層ドキュメント戦略、自律度5段階モデル**: 著者のオリジナル設計
- **SDD の原則（Spec First, Phase Gate, TDD）**: 世界標準の SDD コミュニティの共有知見 [10][12]
- **CC ネイティブ機能の活用パターン**: Anthropic 公式ドキュメント [1][5][6][7] および実践者の知見 [14][15][17][18] に基づく
- **品質データ**: 公開された調査報告 [3][8][26][27][31] に基づく
- **日本品質レイヤー**: 日本のSI業界の実務慣行に基づく著者の設計。工程成果物の区分と合意成熟度は IPA 機能要件の合意形成ガイド [32]、非機能要件の分類は IPA 非機能要求グレード [34] に拠る
- **4層品質ゲート（G1-G4）の構成と順序**: 著者のオリジナル設計。ただし「決定論的検証器 → LLM judge」の順序は Spotify Honk [27]、hold-out による reward hacking 検出は SpecBench [26]、受入条件 → Property → PBT は Kiro [28][29] の実装に基づく
- **証跡パッケージの3区分（証跡 / 参考所見 / 承認）**: 日本のSI の納品・監査慣行に基づく著者の設計

期待効果の数値（工数削減率等）は著者の推定であり、実プロジェクトでの検証はこれからの課題である。
