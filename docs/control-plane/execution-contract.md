# 試作前の実行・判定契約

2026-09-26。著者提案、実行基盤では未実装・未検証。[構想](concept.md)とADR-0001/0005/0006/0007を具体化する。Phase/Gate定義の変更ではない。企業の実PJには現段階で適用せず、[シナリオ](decision-scenarios.md)は合成入力に対する期待値とする。

## 1. 対象と信頼境界

将来の初期対象は共通運営主体に合意できるProgram。運営主体、方針管理者、独立検査発行者、各組織の承認権限、IF所有者/利用者台帳を別々に登録する。運営主体が他社の承認を代行することはできない。閉域・オンプレ・規制業種への対応済みという主張はしない。

作業AIは候補と変更提案のみ作成する。管理資格情報、署名鍵、保護検査・許可台帳の書込み権限を渡さない。検査主体は承認された方針から検査を選び、候補ブランチ内の設定を自己承認させない。Hubは検査・承認を発行せず、その有効性を照合する。記録サービスが正本Gitへ追記した許可を、権限を限定した実行器が確認して使う。

実行・反映経路を既存の認証/保護ブランチ/実行基盤で制限することが前提。ローカルCCの全操作をHubが監視できるとはしない。実行経路を制限できない環境では、成果物検査の範囲に主張を限定する。基盤管理者や信頼した検査発行者の悪用は別の監査課題である。

## 2. 判定に固定する情報

| 記録 | 必須の内容 | 対象が変わったとき |
|---|---|---|
| 対象 | Program/Project/Task、候補成果物集合の内容hash、要求/設計、IF/DB版のベクトル、依存タスク版 | 影響する検査/承認を未確認へ戻す。影響不明も未確認 |
| 方針 | runに適用したプロセス/方針/検査コードと設定のhash、必須/任意/非該当条件、例外可能条件 | 通常改訂は新runから。既存runの方針を変える場合は再検査/再承認 |
| 来歴 | run/command ID、実行器/環境・ツール・Plugin、要求したモデルIDと取得できた応答側ID、入力参照とhash、出力hash、時刻 | 識別子が取得できない項目は未取得。モデル提供側の隠れた版や同一出力の再現を保証しない |
| 検査 | 対象・方針・環境、検査ID、発行主体、結果、実行証拠への固定参照、[署名方式](adr/0008-evidence-envelope.md) | 検査結果自身の改変・未知形式は再発行/再検査が必要 |
| 承認/委任/例外 | 対象、操作、確認可能な本人、権限根拠と版、条件・期限・取消し、根拠証拠 | 対象/条件の変更や期限切れ後は旧記録を流用しない |
| 許可 | 上記記録の集合、判断理由、前提状態、実行世代、期限、保存結果 | 投入/反映直前に再照合。保存未確認の許可は使わない |

対象hashに承認・許可・ログ自身を含めない。対象成果物集合を方針で定義し、その集合は実行者が縮小できない。承認記録の追記だけでは対象hashを変えない。Gitの記録先refと候補成果物refは別々に比較し、後述の競合確認を行う。

機密入力本文や秘密鍵を共有台帳へ保存しない。組織内Gitの権限制限領域に必要な検証記録を保存し、Programには対象hash・方針・結果・発行者・承認有効性の最小マニフェストを共有する。小さな秘密値はhashから推測され得るため、hashの共有可否も情報管理者が判断する。

保存期間、閲覧者、削除時の扱いは情報管理者が導入前に決める（今回は未合意）。削除後は参照先を失った事実を残し、再検証不能な記録から新規許可を出さない。Gitから判断を再構築できる材料を残し、外部の可変URLだけに依存しない。保持と削除要求が両立しない場合は導入条件未達として保留する。

## 3. 判定規則

許可・例外付き許可・保留は対象操作への判定と理由の区分であり、既存Phase/Taskの状態を新設するものではない。

R1: 記録形式・署名・発行者権限・対象・方針・環境の対応を確認する。未知形式、真正性不明、対象不一致、権限外は保留。署名の成功だけではこの条件を満たさない。

R2: 有効方針側の必須集合から照合する。欠落、未実行、unknown、失敗をpassedに数えない。非該当は方針の適用条件と理由を検証する。結果ファイルの一覧だけを母集団にしない。

R3: 実行時刻は信頼できる判定側の時計で確認し、現在時刻が期限以上なら期限切れ。時計/失効台帳を確認できないときは保留。通常改訂で固定runの旧版が自動失効するわけではない。緊急失効は既存runにも適用する。

R4: 条件付き受入・指摘持越しは、方針で例外可能な条件だけを対象とする別記録。対象・残課題・責任者・期限・解消条件・承認権限を検証し、元のfailed/未検証を残した `例外付き許可` とする。例外不可条件、真正性、主体権限、対象の一致は免除できない。未達内容も分からない空の結果を補完しない。今回の合成方針はcoverage未達とローカル必須履歴の未検証だけを例外候補とし、他条件を自動で追加しない。

R5: 委任は委任元の有効権限と、対象・操作・組織・期限の部分集合であることを確認する。初期案では再委任は禁止。元権限の取消し/期限切れで委任も新規許可に使えない。本人確認の根拠は既存認証基盤で検証する。無回答を承認に変えず、期限超過は督促/再計画の対象とする。

R6: 判定入力の状態版を条件に許可/要求をGitへ追記する。競合時は読み直して再判断。保存成功を確認してから送信する。投入・マージ・取込みは許可を最後に検証した実行器だけが担う。実行器は操作の世代と最新失効を検査し、反映対象refを期待SHA付きで更新する。複数の制御処理が同じ外部作用を実行しないよう所有権/世代を確認する。判定と実行の間の競合を排除できない経路は自動実行対象外。これは実装義務で、Gitへの追記だけで原子的な分散実行を実現したとはしない。

R7: 実行応答が不明ならunknownとして隔離し、run/command IDで外部状態を照合する。未知のまま新runを作らない。再送は同じcommand IDとし、実行側の冪等性/照合範囲を確認する。完了を一意に確認した場合は既存結果を検証・記録し、同じ作用をやり直さない。取消し要求は停止確認ではない。遅着結果を旧許可で反映しない。

R8: 共有IF/DBと直接・間接依存を固定し、統合候補全体に対して検査する。枝ごとの成功はマージ後の成功ではない。未知の利用者や競合は影響未確認として保留し、所有者と影響する利用側の確認・必要な移行/切戻しを再計画する。実行枠と人間レビュー枠を別々に管理し、どちらかが満杯なら新規投入を保留する。待ちを減らすために検査を省略しない。

## 4. ローカル回収と実証範囲

成果物再検査の成功は、ローカルの作業順序を遡って証明しない。必須履歴が未検証なら、再実施で証拠を得るか、方針上可能な範囲でR4の例外を記録する。例外なしなら保留。有効な例外があっても履歴は未検証のまま表示する。

今回の文書と合成期待値はOS隔離、認証、暗号実装、実企業の承認実務、性能を実証しない。通常の承認をPhase境界に置く方針を維持し、タスク全件への一律の人間承認を追加しない。将来の試作は、下記シナリオで判定処理そのものを確認してから実行経路の強制を別途検証する。
