# ADR-0005: 中央実行を基本とし、ローカル CC への退避路を残す

## ステータス

提案中

## 日付

2026-09-22

## コンテキスト（背景）

J-SIX Hub の Execution Plane では、タスクごとにコンテナを生成し、CC + J-SIX Plugin で TDD を回し、品質ゲートを通して PR を出し、コンテナを破棄する構成を想定している（[README](../README.md)）。
中央実行にすると、開発者ごとの環境（CC・Plugin・CLAUDE.md・テンプレートの版数）のばらつきをなくせる。

一方で、TDD ループが詰まった場合（仕様の曖昧さ、テスト環境の問題、AI が同じ失敗を繰り返す等）に、人間が手元で調べて直す手段が必要である。
J-SIX 自身も、Hook（ローカル）は最終防衛線にならないため CI（リモート）と二重化するという立場をとっている（[J-SIX.md 4.4](../../J-SIX.md)）。

## 判断（Decision）

- AI の実行は **中央実行（Execution Plane のコンテナ）を基本**とする
- 中央実行で解決できない場合に、人間が **ローカルの CC で作業する退避路を残す**
- ローカルで作った成果物は、**必ず PR としてゲートを再通過して** Hub に戻る。ローカル作業を理由にゲートを省略しない

## 理由（Rationale）

- 中央実行だけにすると、詰まったタスクに人間が介入する手段がなく、プロセスが止まる。想定外の状況で人を支援できなかったことは、プロセス中心型開発環境（PSEE）が定着しなかった理由とされる（出典は M1 で監査。決定事項 D6）
- ローカル作業を許しても、成果物が同じゲートを通るなら、プロセス適合性（[ADR-0002](0002-process-conformance-as-differentiator.md)）は保たれる
- J-SIX 4.4 の「内側ループと外側ループは同じ判定スクリプト・同じ設定を使う」方針により、ローカルと中央で判定がずれない

## 検討した代替案

| 代替案 | メリット | デメリット | 却下理由 |
|---|---|---|---|
| 中央実行のみ | 環境の統一が最も強い | 詰まった時に人間が介入できない | PSEE と同じ硬直に陥る |
| ローカル実行のみ（現状の J-SIX） | 導入が容易 | 環境のばらつき・証跡の散在が解消しない | Hub の目的を満たさない |
| ローカル実行を許し、ゲートは任意 | 柔軟 | 統制の抜け道になる | プロセス適合性が保てない |

## 影響（Consequences）

### ポジティブな影響

- 逸脱（ローカル退避）が起きても、ゲートの再通過によって証跡が揃う
- 状態モデルに「ローカル退避」を逸脱の一種として明示でき、回収の手順を定義できる

### ネガティブな影響（トレードオフ）

- ローカル環境は開発者ごとに異なるため、ローカル作業中の過程（どう直したか）は中央の記録に残らない。残るのは PR とゲート結果である
- ローカル退避が常態化すると中央実行の意味が薄れる。退避の頻度をメトリクスとして観測する必要がある

### 将来の注意事項

- ローカル退避の開始・終了を、状態モデル上の逸脱イベントとして記録する（M2 の `jsix-process.yaml` の「逸脱の種類」に含める）
- 実際の中央実行基盤は本構想のサンプル環境の範囲外である（ADR-0004）
