# ADR-0008: 証跡の署名と現在の有効性を別々に検証する

状態: 提案中（2026-09-26）。実行基盤では未実装・未検証。

## 背景と判断

[ADR-0001](0001-git-as-source-of-truth.md)のGit正本と[ADR-0006](0006-trust-boundaries-and-policy.md)の主体分離を維持する。イベント内容に署名する方式を将来の試作候補とし、暗号方式・鍵管理サービス・認証連携の実装は別計画で決める。Gitの履歴は保管と再構築の根拠で、発行者の真正性や業務上の正しさを自動保証しない。

| 候補 | 確認しやすい範囲 | 限界・判断 |
|---|---|---|
| 保護Gitと署名commit | 取り込んだ内容とcommit署名者 | 検査発行者・承認本人とcommit作成者を同一視できない。保管基盤として維持する |
| イベントごとの署名付き記録（DSSE等） | 個別の内容と発行者を輸送/保管から分離して確認 | 発行権限・信頼ルート・失効を別途管理する必要。将来試作の候補 |
| 第三者保管・透明性ログとの併用 | 記録の公開・監視を追加する選択肢 | 機密・接続・運用コスト、公開可否の合意が必要。初期の必須条件にはしない |

## 発行と利用の条件

1. 独立検査主体は、対象・検査/設定・環境・結果・実行IDを含む記録を発行する。承認記録は本人確認済み操作への証拠と対象・権限を伴う。作業AIが書いた名前や署名形式のJSONを信頼しない。
2. 方針管理者は信頼する発行者/検証鍵と権限範囲を、レビューされた台帳に固定する。秘密鍵はGit/作業AIへ配布せず、発行サービスの管理領域で扱う。鍵IDを自己申告するだけでは登録された権限を得られない。
3. 検証側は受け取った内容の署名を検証し、検証した同じバイト列を判定処理へ渡す。署名後の別JSON再読込・差替えを避ける。形式/許可された署名方式が未知なら保留する。
4. さらに発行者の当該操作権限、対象の一致、必須検査集合、方針・時刻・失効を[実行契約](../execution-contract.md)で照合する。正しい署名による誤った主張もあり得るため、検査の妥当性・権限管理の監査は残る。
5. 鍵ローテーションでは当時の検証鍵と権限根拠を保持する。鍵漏えい等の緊急失効時は、新規投入/反映へ旧鍵の証跡を流用せず、管理者が影響範囲を決めて再検査/再承認する。過去に成功した署名検証の記録は削除しないが、現在の許可には使わない。失効情報を取得できない場合も保留。
6. 検証記録、権限根拠、対象hash、失効、許可の正本はGitへ保存する。機密の本文は権限制限された領域で扱う。保存期間・削除後の再検証不能は導入前に合意する。

## 根拠と限界

[DSSE Envelope 1.0.2](https://github.com/secure-systems-lab/dsse/blob/master/envelope.md)のSecurity considerationsは、署名検証した内容と利用する内容の同一性を要求している。[SLSA v1.2のattestation model](https://slsa.dev/spec/v1.2/attestation-model)は、署名による発行主体の確認と、記録が述べる内容を区別する。2026-09-26確認。ここからのHubへの採用案は著者判断であり、DSSE実装済み、SLSAレベル達成、remote attestation対応という意味ではない。

トレードオフは鍵・主体台帳・権限・失効照合の運用負荷である。署名を加えるだけで実行経路や品質が保証されるとはしない。[ADR-0007](0007-execution-recovery.md)の要求先行記録・照合と併用する。
