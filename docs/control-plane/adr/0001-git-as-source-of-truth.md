# ADR-0001: 正本は Git とし、Hub は Git から再構築できる読み取りモデルだけを持つ

## ステータス

提案中

## 日付

2026-09-22

## コンテキスト（背景）

J-SIX Hub は、J-SIX の工程（Phase・ゲート・承認・証跡）を複数チーム・複数ベンダーにまたがって中央で管理する構想である（[README](../README.md)）。
中央で管理する以上、「工程の状態や成果物の正本をどこに置くか」を最初に決める必要がある。

- J-SIX は Spec + コード + テストを Source of Truth とし、設計書はコードから逆生成する（[J-SIX.md 2.2](../../J-SIX.md)）。整合性は対象版・抽出範囲・記述と組立結果を照合して確認する
- 証跡パッケージは `reports/evidence/<task-id>/` としてリポジトリ内に生成される（[J-SIX.md 第9章](../../J-SIX.md)）
- 並行開発はブランチ・git worktree 単位で行う（J-SIX.md 2.2「並列性」）
- Hub には Web 画面からの承認入力などが発生しうる

## 判断（Decision）

- **正本は Git とする**。Spec / ADR / コード / テスト / 逆生成設計書 / 証跡パッケージ / 承認記録の正本は、いずれもリポジトリ内のファイルである
- Hub が持つのは、工程状態・承認記録・索引などの**読み取りモデル**だけとする。読み取りモデルは Git から**いつでも再構築できる**ことを要件とする
- Hub の Web 画面で行う入力（承認など）は、最終的に**コミットまたは PR**として Git に書き戻す。Hub の DB にだけ存在する事実を作らない

### 承認・検査結果の有効性

Git に保存した記録は、対象の成果物・適用ルールの版、確認可能な承認者または検査の発行元、
判断の根拠と失効・取消し・例外を追跡できることを条件とする。具体的な項目と規則は
[構想 §2.2](../concept.md#22-承認検査結果の対象と有効性著者提案) に定める。
AI が記入した人間名やコミット著者名だけでは人間承認と認めない。対象の変更後は影響する承認・検査を取り直す。
元の記録は履歴として残す。Git を正本とする判断を維持し、保存と真正性・有効性の確認を区別する。

## 理由（Rationale）

- Git にある成果物と別の DB 正本を併用すると、対象版と承認の整合を維持する同期・競合解決の責任が増える。本構想では正本を Git に統一する
- DB でもブランチ・コミットを識別する状態は表せる。ただし Git の履歴と対応させる別モデルの同期が必要になるため、既存のブランチ運用と再構築性を優先する
- 承認記録が Git に残れば、Hub がなくても証跡パッケージは完結する。Hub への依存を持ち込まない（[ADR-0003](0003-dependency-direction-and-process-as-data.md)）
- Hub の読み取りモデルの損失は Git から再構築する。外部実行の結果不明や部分完了の復旧は別の課題であり、ADR-0007 の照合手順を要する

## 検討した代替案

| 代替案 | メリット | デメリット | 却下理由 |
|---|---|---|---|
| Hub の DB を正本にし、Git へはエクスポート | 画面からの編集・集計が容易 | Git の対象版との対応、同期・競合解決が別途必要 | 正本の統一と既存 Git 運用を優先 |
| 成果物は Git、承認記録だけ Hub の DB | 承認 UI を作りやすい | 承認の証跡が Hub に閉じ、証跡パッケージが Hub なしで完結しない | 監査可能性と ADR-0003 の依存方向に反する |
| Git と DB の双方向同期 | 両方の利点 | 競合解決が複雑。どちらが正しいかが曖昧になる | 複雑さに見合う利点がない |

## 影響（Consequences）

### ポジティブな影響

- Hub がなくても、リポジトリだけで工程の状態と証跡を追える
- リプレイ型サンプル（[ADR-0004](0004-replay-sample-environment.md)）は Git 履歴を実測データとして使える

### ネガティブな影響（トレードオフ）

- 画面からの承認がコミット / PR を経由するため、反映に遅延がある
- 読み取りモデルの再構築処理（Git → 状態）を Hub が持つ必要がある
- 承認記録のファイル形式（どこに・どの形式で書くか）を別途定義する必要がある

### 将来の注意事項

- 承認記録の形式は、証跡パッケージの「承認」区分（J-SIX.md 9.1）と揃える
- 読み取りモデルに含めてよいのは「Git から導出できるもの」だけである。メトリクスのキャッシュ等を追加する際もこの条件を確認する
