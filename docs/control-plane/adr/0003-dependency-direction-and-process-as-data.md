# ADR-0003: 依存は Hub → J-SIX の一方向とし、プロセス定義をデータ化して J-SIX に置く

## ステータス

提案中

## 日付

2026-09-22

## コンテキスト（背景）

J-SIX の設計原則の第一は **CC ネイティブ**（外部フレームワークに依存せず、CC のネイティブ機能のみで構築する）である（[J-SIX.md エグゼクティブサマリー](../../J-SIX.md)）。
J-SIX は現在、Plugin 単体で個人〜小規模チームが使える。

Hub を導入すると、Phase・ゲート・成果物・遷移の定義を Hub 側でも扱う必要が出る。
このとき定義を Hub に持たせると、次の問題が起きる。

- J-SIX の Plugin と Hub で、同じプロセスの定義が二重に書かれ、ずれる
- 「J-SIX を使うには Hub が必要」という依存が生まれ、CC ネイティブの原則と矛盾する

## 判断（Decision）

1. **J-SIX は Hub に依存しない**。Plugin 単体で J-SIX が回る状態を維持する。依存は **Hub → J-SIX の一方向** のみとする
2. **プロセス定義をデータ化して J-SIX に置く**。`process/jsix-process.yaml`（＋ JSON Schema）に Phase・ゲート（決定論的チェック＋人間承認）・成果物・役割・遷移・逸脱の種類を記述する
3. Plugin と Hub は、いずれもこの yaml を参照する側とする。Hub は **J-SIX の版数（タグまたはコミット SHA）を指定して** 取り込み、コピーして独自に改変しない

## 理由（Rationale）

- 「J-SIX はツールに依存しないプロセス定義であり、Hub はその実装の一つ」という関係を、文章ではなくリポジトリの構造で表せる
- 版数を指定して取り込むことで、Hub がどの版のプロセスに従っているかを追跡できる
- yaml の正は `docs/J-SIX.md` から導出する。J-SIX.md とプロセス定義の二重管理にならないよう、矛盾があれば J-SIX.md を正とする

## 検討した代替案

| 代替案 | メリット | デメリット | 却下理由 |
|---|---|---|---|
| プロセス定義を Hub 側に持つ | Hub の開発が速い | Plugin と定義が二重化。J-SIX が Hub の存在を前提にしがち | 依存方向が逆転する |
| 定義をデータ化せず、Hub が J-SIX.md を読んで解釈 | 追加ファイル不要 | 自然文からの抽出は決定論的でない | ゲート判定の根拠にできない |
| Hub に yaml をコピーして使う | 取り込みが簡単 | コピー後に独自改変されやすく、版の追跡が切れる | 版数指定の取り込みで足りる |

## 影響（Consequences）

### ポジティブな影響

- Hub がなくても J-SIX は使える。Hub の開発が止まっても J-SIX 本体に影響しない
- サンプル環境の Phase・ゲート表示を yaml から生成でき、ハードコードを避けられる

### ネガティブな影響（トレードオフ）

- J-SIX.md と yaml の整合を保つ作業が増える。CI でのスキーマ検証と、変更時の照合が必要
- Plugin が yaml を参照する実装は今回の範囲外であり、当面は Plugin 側の記述と yaml が並存する

### 将来の注意事項

- Plugin からの参照は M2 では設計メモのみとし、実装は Plugin 側の別作業として ROADMAP に追記を提案する
- yaml を変更したらタグを打ち、Hub 側の取り込み版数を明示的に上げる
