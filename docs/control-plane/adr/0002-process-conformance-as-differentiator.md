# ADR-0002: 差別化軸を「プロセス適合性の統制」とする

## ステータス

提案中

## 日付

2026-09-22

## コンテキスト（背景）

「AI エージェントを中央で動かし、統制する基盤」は、それだけでは新規性がない。
ベンダー製品として、GitHub Agent HQ や GitHub Enterprise の AI Controls（agent control plane）などが既に提供されている（出典は未監査。[REFERENCES_AUDIT](../../REFERENCES_AUDIT.md) への登録は M1 で行う）。

これらの製品が扱うのは、主に「誰が・どのエージェントが・何にアクセスできるか」というアクセス統制である（著者の理解。M1 で確認する）。
一方、J-SIX が大規模・複数ベンダー案件で問題にしているのは次の点である。

- Skill の実行タイミングや Phase の順序が個人の判断に委ねられている
- 承認・レビュー・ゲート判定・証跡が各自の PC とリポジトリに散在し、工程を経たかどうかを横断的に確認できない

## 判断（Decision）

J-SIX Hub の差別化軸を **プロセス適合性の統制** とする。すなわち、
「正しい工程を、正しい順序で経て、その証拠が残っているか」を統制の対象にする。

アクセス統制（認証・権限・エージェントの利用可否）は Hub の主眼にしない。必要な場合は既存製品と組み合わせる前提とする。

## 理由（Rationale）

- 契約型（受発注）の開発では、工程を経たことの証明そのものが納品物の一部になる（J-SIX.md 6.2、第9章）。アクセス統制ではこれを示せない
- J-SIX は既に、Phase・品質ゲート（G1〜G4）・証跡パッケージという「工程を経た証拠」の仕組みを持つ。Hub はこれを複数チームに広げる位置にあり、J-SIX の強みと一致する
- アクセス統制の領域で既存製品と競合しても、個人の方法論プロジェクトに勝ち目はない

## 検討した代替案

| 代替案 | メリット | デメリット | 却下理由 |
|---|---|---|---|
| 中央でエージェントを動かす実行基盤そのものを主張する | 分かりやすい | 既存製品・既存研究と差がない | 新規性がない |
| アクセス統制とプロセス統制の両方を主張する | 網羅的 | 焦点がぼやけ、実装範囲が肥大化する | スコープの肥大化 |

## 影響（Consequences）

### ポジティブな影響

- 構想文書・論文の主張が一本に絞られる
- サンプル環境で見せるべきもの（Phase 遷移、ゲートでの停止、承認、逸脱と回収、証跡）が明確になる

### ネガティブな影響（トレードオフ）

- 認証・権限など、実運用に必須の機能を Hub の範囲外に置くことになる。実運用の話をする際は既存製品との組み合わせを前提として説明する必要がある

### 将来の注意事項

- 「既存製品・既存研究にプロセス適合性の統制が見当たらない」という判断は、限定的な調査に基づく。M1 の関連研究調査（SASE の被引用追跡、ICSSP 系、PSEE 系）で裏付けるか、主張を修正する
- プロセス中心型開発環境（PSEE）は同じ発想の直接の祖先であり、想定外の状況に対応できなかったことが定着しなかった理由とされる（出典は M1 で監査）。この教訓への回答（逸脱の許容。決定事項 D6）を差別化の説明に必ず含める

### H1 の調査結果（2026-09-22）

- **製品との比較**：GitHub Agent HQ / Enterprise AI Controls の統制の中心はポリシー・監査ログ・アクセス管理であり、
  本 ADR の特徴づけは概ね妥当だった。ただし既存のブランチ保護・必須チェック・PR 承認はエージェントにも適用される。
  Kiro・Spec Kit は開発者ツールの内側にフェーズ構造を持つが、組織として順守を検証・監査する仕組みは確認できなかった
- **研究との比較**：フェーズ状態機械でエージェントの工程を外部から統制する研究は、2026年に既に出ている
  （concept.md §6.4）。したがって「プロセス適合性の統制」**そのもの**は研究に対する新規性にならない。
  研究に対しては、契約型開発への適用と4点の組み合わせ（concept.md §6.6）を差別化の軸として説明する
- 本 ADR の判断（アクセス統制ではなくプロセス適合性を統制の対象にする）は変更しない
