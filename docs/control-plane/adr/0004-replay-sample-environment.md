# ADR-0004: サンプル環境は実際の J-SIX 実行記録を再生するリプレイ型とする

## ステータス

提案中

## 日付

2026-09-22

## コンテキスト（背景）

J-SIX Hub の構想を記事・論文で説明するために、Hub を導入すると開発者がどう統制され、開発がどう進むのかを画面で見せたい。
ただし現段階は方法論レベルの提案であり、実案件への適用は行わない。

見せ方には次の選択肢がある。

- 実際に AI を動かす Hub を作る
- 架空のデータで画面を作る（モック）
- 実際の J-SIX 実行記録を Hub の画面上で再生する（リプレイ）

J-SIX は推定と実測を切り分ける方針をとっている（期待効果の「検証ステータス」列、[J-SIX.md エグゼクティブサマリー](../../J-SIX.md)）。
また、`examples/approval-workflow` と `examples/monthly-billing` には、J-SIX を一周した実行記録（Git 履歴、ゲート結果、証跡パッケージ等）が残っている。

## 判断（Decision）

- サンプル環境は**リプレイ型**とする。実際の J-SIX 実行記録（まず `examples/approval-workflow` の一周分）を、Hub の画面上で時系列に再生する
- 実際の AI（CC / Agent SDK）は起動しない。静的な Web アプリとし、バックエンド・DB・認証・編集機能は持たない
- 画面上に「リプレイ（実際の AI は動作していません）」を**常時表示**する
- 各イベントに **provenance ラベル**（`measured` 実測 / `reconstructed` 再構成）を付け、画面にも表示する。Git 履歴やテスト結果など記録から導出したものは実測、当時 Hub が存在しなかったために組み立てたもの（Hub によるタスク投入、Hub 上の承認操作など）は再構成とする
- 複数チーム・Interface Contract を見せるための架空シナリオを作る場合は、全イベントを再構成とし、画面上でも架空であることを明示する

## 理由（Rationale）

- 実測に基づくため、完全な架空データより学術発表・記事での説得力が高い
- 推定と実測を切り分ける J-SIX の方針と一貫する
- 実際の AI を動かさないので、API 費用・認証・セキュリティの問題を持ち込まずに公開できる

## 検討した代替案

| 代替案 | メリット | デメリット | 却下理由 |
|---|---|---|---|
| 実際に AI を動かす Hub を作る | 最も説得力がある | 構築・運用の負担が大きい。公開すると費用とセキュリティの問題が出る | 現段階（方法論の提案）に対して過大 |
| 完全な架空データのモック | 見せたい場面を自由に作れる | 実測の裏付けがない | 推定と実測を分ける J-SIX の方針に反する |
| 画面を作らず、文書と図だけで説明 | 最も軽い | 統制が時間とともにどう働くかが伝わりにくい | 構想の伝達力が不足する |

## 影響（Consequences）

### ポジティブな影響

- ADR-0001（正本は Git）に従い、Git 履歴をそのまま実測データとして使える
- 画面の Phase・ゲート表示を `jsix-process.yaml` から生成することで、プロセス定義の妥当性も同時に示せる

### ネガティブな影響（トレードオフ）

- 当時 Hub が存在しなかったため、Hub 固有のイベント（タスク投入、Hub 上の承認、エスカレーション）の多くは再構成になる。実測の比率が低くなりうる
- 実行記録にイベント単位のログが不足していれば、Plugin にイベント出力用 Hook を追加して再実行する必要がある（M3 で確認する）

### 将来の注意事項

- 再構成イベントを「実測」と誤認させる表示をしない。README・記事・論文でも同様に区別する
- 実行記録から個人情報・秘密情報・ローカルの絶対パスをリプレイ用データに持ち込まない
