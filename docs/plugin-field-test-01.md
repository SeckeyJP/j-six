# Plugin 実動検証 #1 — 7 Skill をヘッドレスで実行する

**実施日**: 2026-09-19 ／ **対象**: j-six Plugin（v2.1 開発版）の Skill 7本 ／ **題材**: `examples/approval-workflow/`
**位置づけ**: ROADMAP C2「各 Skill の実行ログ取得」

J-SIX の Plugin は、Skill・Agent・Hook の定義と決定論的チェックのスクリプトで構成される。
スクリプトには単体テストがあるが、**Skill と Hook を Claude Code に実際に読み込ませて
動かしたことは無かった**。本検証では、Plugin を読み込んだ Claude Code をヘッドレスで起動し、
J-SIX の工程順に Skill を1本ずつ実行した。

結論を先に書く。**Plugin は、読み込まれることすら無い状態だった。**それを直した後も、
実行するたびに新しい不具合が見つかり、合計8件を修正した。大半は単体テストでは
検出できない種類のもの（Claude Code の仕様との食い違い、実行環境との相互作用）である。

---

## 1. 方法

`examples/approval-workflow/` を作業ディレクトリにして、次の形で1本ずつ起動した。

```bash
claude -p "/j-six:<skill> <指示>" --plugin-dir ../../plugin \
  --output-format stream-json --verbose \
  --permission-mode acceptEdits --allowedTools "Read,Write,Edit,...,Bash(make:*),..." \
  < /dev/null
```

- ヘッドレスでは対話できないため、人が判断すべき事項（例: 不在の申請は 404 を返す）は
  プロンプトで「合意済み」として渡した
- コミットは `tdd-cycle` だけに許可した（Skill の手順がフェーズごとのコミットを前提とするため）。
  push はすべての実行で禁止した
- 起動時の `init` メッセージで、Plugin の読み込み成否（`plugins` / `plugin_errors`）を毎回確認した

## 3. 見つかった Plugin の不具合（すべて修正済み）

| # | 発見した実行 | 不具合 | 影響 | 修正 |
|---|---|---|---|---|
| 1 | 0 | `plugin.json` の `repository` がオブジェクト | **Plugin 全体が読み込まれない**（Skill・Agent・Hook のどれも動かない） | 文字列に修正。CI に `claude plugin validate` |
| 2 | 1 | prompt 型 Hook を「〜なら…せよ。該当しなければ何も出力しない」という指示文で書いていた | prompt 型 Hook は `{ok, reason}` を返す評価器であり「何も出力しない」選択肢が無い。**Stop が毎回ブロックされ28回繰り返した** | ADR 提案 Hook を評価器の形に。重複・条件の無い4つを削除 |
| 3 | 2 | Skill がリポジトリルートの `templates/` を参照 | **インストールされた Plugin では Skill が動かない**（Plugin ディレクトリしかコピーされない） | テンプレートを Skill に同梱（`${CLAUDE_SKILL_DIR}`）。同期スクリプトと CI 検査 |
| 4 | 2 | `` !`cat` `` で同梱テンプレートを読んでいた | 作業ディレクトリ外のファイルはセキュリティ制約で読めない（インストール先も作業ディレクトリ外） | Read ツールで読む指示に変更 |
| 5 | 2 | 工程上いま満たせないゲート失敗（テストは次工程で書く）で Stop がブロックし続ける | 15回繰り返し、Claude Code の上限（進捗なし8回）も効かなかった | 同じ失敗が3回続いたら停止を許可。判定は緩めず CI で止める |
| 6 | 3 | 変更ファイルを未コミットの差分だけで数えていた | **フェーズごとにコミットするとスコープ検査は0ファイル、G3 はスキップ**。前タスクの判定が残っていても通る | G3 はブランチの分岐点から、スコープは RED タグからの差分で判定。G3 の判定を差分の指紋に紐づける |
| 7 | 6 | format Hook が拡張子を見ずに `ruff format` を実行 | `judge.json` を Python として整形し **JSON を壊した** | 対象を `hook_files` で宣言させる |
| 8 | 6 | format Hook を編集の前（PreToolUse）に実行 | 直後の Write / Edit が「読んだ後に変更された」で失敗 | 編集の後（PostToolUse）に移動 |

#5 と #6 の修正は緊張関係にある。#5 はゲートを「解除しすぎない」ための上限、#6 はゲートが
「空振りしない」ための修正で、どちらも品質ゲートを**正しく効かせる**方向の変更である。
判定の基準そのもの（閾値・deny）は一切緩めていない。

#2・#5 は、止めすぎる Hook は運用で Hook ごと無効にされる、という品質ゲートのランナー自身の
設計方針（Stop のたびにビルドやテストを走らせない理由）を、J-SIX の Plugin が破っていた例でもある。

## 5. 所見

- **単体テストは「部品が仕様どおりか」しか保証しない。**8件のうち、スクリプトの単体テストで
  防げたのは #6 と #7 の一部だけだった。残りは Claude Code の仕様（マニフェスト、prompt 型 Hook の
  意味、Plugin のインストール方式、`!` 展開のセキュリティ制約、Hook のタイミング）との食い違いで、
  **実際に読み込ませて動かさない限り見つからない**
- **子セッションは不正な近道を取らなかった。**spec-create は、ID を書いただけの偽テストで
  トレーサビリティを通すことを拒否し、ブロックされ続けることを選んだ。tdd-cycle は、ゲートが
  通ったことを成果として報告せず、ゲートが空振りしていることを報告した
- **ヘッドレス実行は Plugin の回帰テストになる。**1本 $1.5〜15 のコストがかかるため毎回は回せないが、
  Plugin を変更したときの受入試験として使える。今後は `claude plugin eval` の評価ケースへの移行を検討する
