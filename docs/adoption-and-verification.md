# 適用条件と検証戦略

2026-09-26。著者による導入準備の提案。企業の実PJへの適用・複数組織での実証は現段階では行っていない。今回の確認対象は既存サンプルと合成例であり、下記の合意を取得済みという意味ではない。

本書は[J-SIX](J-SIX.md) Phase 1/2/5の補足で、Phaseの順序、ゲート、自律度の定義を追加・変更しない。[記入テンプレート](../templates/verification/strategy.md)と[記入例](verification-examples.md)を使い、Spec/ADRの正本へ参照で結ぶ。

## 1. 採用する範囲を合意する

将来の案件では、次の各項目を権限のある担当者が確認する。未合意は未合意と記録し、その範囲のAI実行や従来成果物の置換を開始しない。契約・組織規程の解釈を本書で代行しない。

| 項目 | 確認する役割 | 合意・記録する内容 | 条件を満たせない場合 |
|---|---|---|---|
| 事前設計 | 発注側の設計承認者・設計責任者 | 提出時期、章、必要な詳細度、代替物、承認対象版 | 必要な従来設計書を作成・承認してから実装。二重作成工数も計上 |
| 受入・責任分界 | 発注側の受入責任者・各社責任者 | 検収対象、品質条件、欠陥対応、IF所有者、再検査と変更合意 | 責任者不在の境界を自動で通過させない |
| AI利用 | 各社の利用許可責任者 | 利用可能な実行環境・モデル・送信対象・禁止用途 | 許可された範囲の補助利用または従来作業に限定 |
| 情報管理 | データ所有者・情報管理者 | 機密区分、送信先、閲覧者、保存先・期間、削除、監査方法 | 実データを持ち込まない。合成データへの置換も妥当性を確認 |
| 品質判定 | QA責任者・受入責任者 | 要求別の判定、未検証の扱い、例外権限、残課題の期限 | 未実行・ID出現だけを合格としない |
| 実行とレビュー容量 | 開発責任者・レビュー責任者 | 担当・稼働枠、待ちの上限、投入停止と再開条件 | 新規投入を絞る。無承認で確認範囲や品質条件を下げない |

共通のCLAUDE.mdやPluginは手順を共有する手段であり、各社の責任や同一品質を自動保証しない。費用削減の配分は価格・契約条件によるため、工数減と売上減を同一視しない。

## 2. 要求解釈と検証を分離する

| 確認面 | 主な入力 | 担う役割・出力 | 残る限界 |
|---|---|---|---|
| 要求の妥当性 | 業務資料、要求の出典、合意した受入条件 | 業務責任者がSpecとの相違・曖昧さを解消 | 業務資料自身の誤りは別途照合が必要 |
| テスト設計 | 要求原典、境界条件、反例 | 実装担当と別の検証担当が期待結果を導出 | 別担当・別モデルでも同じ前提を誤る可能性 |
| 実装の適合 | 固定対象版、保護したテスト・検査設定 | 独立検査担当が実行結果・失敗・未実行を記録 | hold-out保護は要求自体の正しさを証明しない |
| 業務受入 | 原典から導いた業務シナリオと対象版 | 受入責任者が業務結果を確認 | AIの肯定や高カバレッジは承認の代わりにならない |

役割の分離とアクセス制御による隔離を区別する。1人のサンプルでは別コンテキストのAIレビューを使えても、独立組織による検証・業務受入の実証にはならない。期待結果を実装からコピーして作らない。要求ID、テストの存在、対象版での実行、期待値の意味的対応をそれぞれ確認する。

## 3. 準備を上流から始める

Phase 1で要求・受入役割・非機能分類と未合意事項を洗い出す。Phase 2で試験環境、データ、責任、入口/出口、事前設計の承認対象を具体化する。Phase 4で単体・結合等の検査を実施し、Phase 5で独立検査・業務受入・残課題をまとめて判定する。試験設計をPhase 5まで待たない。

| 確認する領域 | 検証戦略に最低限残す事項 |
|---|---|
| 単体・結合・システム・受入 | 原典/REQ、対象版、責任者、データ、環境、入力と期待結果、入口/出口 |
| 外部IF・バッチ・帳票 | 相手側の版/所有者、重複・順序・欠落・再送、締め境界、出力内容・表示、ジョブ再開 |
| 性能・拡張性 | 負荷の分布、件数、同時数、時間/資源の測定方法、目標の根拠 |
| 可用性・障害復旧 | 障害点、復旧時間/欠損許容量の合意、照合、二重処理、部分完了 |
| 移行 | 対象/対象外、元データと変換規則、件数・金額等の照合、リハーサル、切戻し判断と責任 |
| 運用・保守・セキュリティ・設置環境 | 権限、監査、監視、手順、引継ぎ、保存・削除、設置制約、適用外の理由 |

分類の検討には[IPA非機能要求グレード](https://www.ipa.go.jp/archive/digital/iot-en-ci/jyouryuu/hikinou/ent03-b.html)を参照できる。全分類に同じ試験や閾値を要求するものではない。対象外・未実装・未実行を区別し、対象外の理由と決定役割も記録する。

## 4. レビュー対象と容量

課金・重大業務・権限・データ喪失・移行/切戻し・共有IF等は、影響が大きい変更として必要な専門確認を指定する。生成元がコードでも、誤記・欠落・変換誤りを確認する。レビュー重点は由来だけでなく業務影響・不確実性・変更範囲で決める。

残余を抽出確認する場合は、母集団、対象版、抽出単位、方法、選定理由、未確認範囲、発見時の追加確認条件を残す。都合のよい成功例だけを選ばない。標本設計を満たさない抽出から、未確認部分を含む統計的保証を主張しない。

待ち件数・最古待ち時間・再レビュー量を観測し、容量不足時は投入抑制、担当追加、粒度調整を行う。要求やテスト変更時には影響する判断を未確認へ戻し、再確認する。これは案件の人間レビュー設計であり、作業環境で必須とする計画・成果物の独立レビューを免除する規則ではない。

品質要求は維持する。バグ密度・レビュー密度・カバレッジ等の代理指標は分母と測定条件を確認し、AI生成量の変化に対して従来閾値が妥当かを試行で評価する。根拠なく新閾値を発明しない。全工程の工数・失敗を含めた評価設計は別の補足で具体化する。
