# ケーススタディ #1 — 申請承認ワークフローで J-SIX を一周する

**Author**: H.Sekita | **Date**: 2026-06-14 | **題材**: 申請承認ワークフロー（FastAPI / Python）

> J-SIX のこれまでの数値は**すべて著者推定**だった（README 参照）。本ケーススタディは、
> 小さな実題材で J-SIX を Phase 1→6 まで一周し、**実測できる指標と推定にとどまる指標を
> はっきり分けて**提示する試みである。成果物は [`examples/approval-workflow/`](../examples/approval-workflow/)
> に動く形で置いてある（テストが通り、サーバが起動する）。

---

## 1. 題材と狙い

備品・経費の申請承認ワークフロー。日本の SI で頻出の「稟議・承認」業務であり、

- 金額に応じた承認段数、承認順序の強制、自己承認の禁止 → **明確な業務ルール**（TDD 向き）
- 状態遷移と監査ログ → **統制要件**（ADR・逆生成設計書が映える）

を持つ。規模は意図的に小さく抑え（ドメイン+API で約350行）、プロセスの一周を観察できる
最小単位とした。

## 2. J-SIX の一周

| Phase | 実施したこと | 成果物 |
|---|---|---|
| P1 要求合意 | 業務ルールを REQ-001〜010 として確定 | [`requirement-spec.md`](../examples/approval-workflow/docs/requirement-spec.md) |
| P2 技術設計 | 「ルールを workflow.py に集約」する設計を決定 | [`design-spec.md`](../examples/approval-workflow/docs/design-spec.md) + ADR-0001/0002 |
| P3 タスク分解 | 要件をテスト単位に分解（REQ ⇔ test） | — |
| P4 TDD 実装 | テストを先に書き（37件）、`app/` を実装 | [`tests/`](../examples/approval-workflow/tests/) / [`app/`](../examples/approval-workflow/app/) |
| P5 品質検証 | カバレッジ計測・品質ゲート判定 | 下表 |
| P6 ドキュメント | 逆生成（Swagger）+ トレーサビリティ | [`traceability.md`](../examples/approval-workflow/docs/traceability.md) |

## 3. 実測できた指標（再現可能）

以下は `examples/approval-workflow/` で `pytest --cov` を実行すれば誰でも再現できる**実測値**。

| 指標 | 実測値 | 計測方法 |
|---|---|---|
| アプリ実装 | **354 行**（app/） | `wc -l app/*.py` |
| テストコード | **290 行**（tests/） | `wc -l tests/*.py` |
| テスト件数 | **37 件** | `pytest --collect-only` |
| ステートメントカバレッジ | **99%**（207 stmt 中 未到達 2） | `pytest --cov=app` |
| 要件トレーサビリティ | **10/10 要件にテスト存在**（未トレース 0） | `traceability.md` |
| テスト/実装 行数比 | **0.82**（テストが実装の約8割の量） | 算出 |

### 観察

- **テスト/実装比 0.82** は「テストファーストで業務ルールを先に固定する」J-SIX の実装像と
  一致する。ルールの数（REQ 10件）がテスト数（37件）に展開され、各 REQ が平均3〜4ケースで
  検証されている。
- **カバレッジ 99%** は品質ゲート（95%）を満たす。未到達2行はディフェンシブな分岐
  （到達しにくい早期 return）で、テストの薄さではない。
- **逆生成（P6）の完全性**: API 仕様は FastAPI が `/docs`（OpenAPI）として自動生成する。
  「コードが Source of Truth、設計書は逆生成」という J-SIX の主張が、IF 設計書については
  文字どおり成立する（手書き IF 設計書はゼロ）。

## 4. 推定にとどまる指標（実測できなかったもの）

J-SIX が掲げる効果のうち、本ケーススタディでも**実測できなかった**ものを正直に記す。

| 指標 | J-SIX の主張 | 本ケースでの扱い |
|---|---|---|
| 実装工数 60-70% 削減 | 著者推定 | **未実測**。比較対象（人手のみの実装時間）を取っていないため、削減率は出せない |
| 設計書⇔コード乖離ゼロ | 原理的にゼロ | IF 設計書は逆生成で乖離ゼロを**確認**。一方、業務背景（Why）を書いた Spec/ADR は逆生成できず、人手更新が必要＝乖離リスクは残る |
| カバレッジ 85-95% | TDD 全面適用時 | 本ケースは **99% を実測**したが、N=1 かつ小規模。一般化はできない |

### 結論として言えること / 言えないこと

- **言える**: J-SIX のプロセスは小規模題材で実際に一周でき、テスト網羅・トレーサビリティ・
  IF 設計書の逆生成は**実物として成立する**。
- **言えない**: 「工数 60-70% 削減」は本ケースでも依然 N=0 の推定。これを実証するには
  同一題材を「人手のみ」「J-SIX」の両方で実装し時間を計測する A/B 比較が必要（次の課題）。

## 5. 次のアクション（ROADMAP へ反映）
