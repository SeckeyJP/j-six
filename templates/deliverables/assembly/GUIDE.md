# 組立ガイド — 工程成果物を顧客様式の設計書に束ねる

工程成果物27点は「作る単位」であって「提出する単位」ではない。顧客が求めるのは
「基本設計書」「詳細設計書」「ユーザインタフェース設計書」のような**顧客側の様式**であり、
その目次は顧客ごとに違う。本ガイドは、工程成果物から顧客様式の設計書を組み立てる手順を定める。

IPA 自身が、外部設計工程に業界標準の工程成果物は無く、工程成果物と設計書は1対1ではないと
明記している（[IPA 機能要件の合意形成ガイド](https://www.ipa.go.jp/archive/files/000004517.pdf)
概要編 2.1）。したがって「正しい基本設計書の目次」は存在しない。**存在するのは、顧客の目次と
工程成果物の対応表だけである。**

| ファイル | 内容 |
|---|---|
| [`GUIDE.md`](GUIDE.md) | 本書。組立の原則と手順 |
| [`kihon-sekkei.md`](kihon-sekkei.md) | 組立例: 基本設計書（外部設計） |
| [`shousai-sekkei.md`](shousai-sekkei.md) | 組立例: 詳細設計書（内部設計） |

## 1. 原則

### 1.1 正は工程成果物にある。設計書はその「ビュー」である

束ねた設計書を直接編集しない。修正は**工程成果物の側**で行い、逆生成するものは**さらにその
逆生成元（コード・受入テスト・Spec）**で行ってから組み立て直す。

```
逆生成元（コード / 受入テスト / Spec / ADR）   ← 修正はここ
        ↓ 逆生成 or 人手
工程成果物27点（docs/deliverables/）           ← 正
        ↓ 組立（本ガイド）
顧客様式の設計書（docs/design-docs/）          ← ビュー。編集しない
```

設計書を直接直すと、次回の逆生成で修正が消えるか、工程成果物と設計書が食い違う。
これは従来の「設計書とコードの乖離」をもう1段下に作り直すことに等しい。

### 1.2 由来の表示を落とさない

各工程成果物の冒頭にある**由来**（コードから逆生成 / 受入テストから逆生成 / 併用 / 人手）は、
束ねた後も章ごとに残す。顧客レビューで重点を置くべきは**人手で書いた章**であり、逆生成した章は
「実装がこうなっている」という事実の記述である。由来が見えないと、レビュアーは27点すべてを
同じ重みで読むことになる。

### 1.3 ID を変えない

`SCR-nnn` / `RPT-nnn` / `EIF-nnn` / `BATCH-nnn` / `REQ-nnn` / `PROP-nnn` などの ID は、
束ねるときに振り直さない。顧客様式に独自の採番がある場合は**併記**する。ID はテスト名と
コードに書かれたトレーサビリティ・キーであり、振り直すとコードとの対応が切れる。

### 1.4 「該当なし」の章を消さない

対象システムが持たない領域（API のみのシステムの画面・帳票など）は、章を消さずに
「該当なし（理由）」と書く。章が無いと、抜けなのか対象外なのかを顧客が区別できない。

### 1.5 同じ情報を2冊に書かない

基本設計書と詳細設計書の両方に同じ工程成果物（エンティティ定義など）を入れたくなる場合は、
**一方にだけ置き、もう一方からは参照する**。両方に全文を載せると、片方だけが更新されたときに
2冊が食い違う。

## 2. 組立定義の書式

組立定義は「顧客様式の章 → 構成要素」の対応表である。本ディレクトリの
[`kihon-sekkei.md`](kihon-sekkei.md) と [`shousai-sekkei.md`](shousai-sekkei.md) がこの書式の例。

| 列 | 内容 |
|---|---|
| 章 | 顧客様式の章番号と章題（顧客の目次のとおりに書く） |
| 構成要素 | 工程成果物の番号（①〜㉗）、Spec の節、ADR、証跡パッケージのファイル |
| 由来 | 構成要素の由来（1.2） |
| 事前提出 | Phase 2 の時点で出せるか（3 参照）。出せない場合は代わりに何を出すか |

構成要素は、次の5種類のいずれかに必ず対応させる。どれにも対応しない章は4の手順で扱う。

| 種類 | 置き場所 | 由来 |
|---|---|---|
| 工程成果物（27点） | `docs/deliverables/` | 成果物ごとに異なる |
| 要求 Spec / Design Spec の節 | `docs/specs/` | 人手（第1層） |
| ADR | `docs/adr/` | 人手（第2層） |
| 証跡パッケージ | `reports/evidence/<タスクID>/` | 決定論的な実行結果 |
| トレーサビリティマトリクス | `docs/traceability.md` など | 逆生成 |

---

## 3. 提出の時期は2回ある

顧客が設計書を求める時期は、**実装前（事前設計書）**と**納品時**の2回ある。J-SIX では
逆生成する成果物がコードから作られるため、**事前提出の時点では19点がまだ存在しない**。
組立定義には、事前提出で何を出すかを章ごとに書いておく。

| 時期 | J-SIX の Phase | 出せるもの | 合意成熟度 |
|---|---|---|---|
| 事前提出 | Phase 2 品質ゲート（設計レビュー） | 人手の5点、要求 Spec、Design Spec、ADR、**実動プロトタイプ** | 充実レベル |
| 納品 | Phase 6 | 27点すべて（逆生成の19点を含む）、証跡パッケージ | 完成レベル |

合意成熟度の3段階は IPA ガイド 3.1.1 による。各レベルと J-SIX の Phase の対応は
[`../README.md`](../README.md) の「合意成熟度」を参照。

事前提出では、逆生成する章に**代替物**を入れる。画面なら実動プロトタイプの画面キャプチャと
Design Spec の画面一覧、データなら Design Spec の ER 概要、といった形である。その章には
「本章は Phase 6 に実装から逆生成した版に差し替える」と明記する。**事前提出版の内容を
納品版に手で書き写して延命させない。**納品版は逆生成で作り直す。

この扱いは J-SIX.md 6.5「顧客が事前設計書を求める場合」の短期策（Design Spec ＋
プロトタイプを基本設計書相当として提出する）を、章単位に具体化したものである。

## 4. 顧客様式への組み替え手順

1. **顧客の目次を入手する。** 過去案件の設計書、顧客の標準様式、RFP の納品物一覧のいずれか。
   J-SIX 側で目次を作って提案するのは、顧客に様式が無い場合だけにする
2. **章ごとに構成要素を対応付ける。** [`kihon-sekkei.md`](kihon-sekkei.md) を出発点にして
   顧客の章題に置き換えるのが早い
3. **どれにも対応しない章を3つに分類する。**

   | 分類 | 例 | 扱い |
   |---|---|---|
   | (a) 27点の外に既知の置き場所がある | システム構成、非機能、セキュリティ | Design Spec の節か ADR を構成要素にする |
   | (b) J-SIX では作らない | 実装前に書く関数単位の処理記述 | 作らない理由と代替物を顧客と合意し、章に明記する |
   | (c) 新たに人手で書く必要がある | 移行計画、運用手順 | 人手の成果物として追加し、由来を「人手」と表示する |

   (c) が増えるほど乖離リスクが残る章が増える。(c) を足す前に、Spec か ADR に書くべき内容で
   ないかを確認する
4. **組立定義をプロジェクトに保存する。** `docs/design-docs/assembly-<設計書名>.md` に置き、
   Phase 2 の品質ゲートで顧客と合意する。**目次の合意は設計書の中身より先に取る**
5. **組み立てる。** 組立定義の順に構成要素を連結し、章ごとに由来を表示する（1.2）
6. **組立後の検査を行う**（5 参照）

### 例: ユーザインタフェース設計書

IPA ガイドが例示している束ね方（同ガイド 概要編 2.1）。

| 章 | 構成要素 | 由来 |
|---|---|---|
| 1. 画面レイアウト | ⑦ [画面レイアウト](../screen/03-screen-layout.md) | コードから逆生成 |
| 2. 画面入出力項目 | ⑧ [画面入出力項目一覧](../screen/04-screen-io-items.md) | コードから逆生成 |
| 3. 画面アクション | ⑨ [画面アクション明細](../screen/05-screen-actions.md) | コードから逆生成 |

3点がいずれも逆生成なので、この設計書は**事前提出の時点では代替物しか出せない**。
事前提出では実動プロトタイプを見せ、この設計書は納品時に出す、と合意するのが現実的である。

## 5. 組立後の検査

- [ ] 27点のうち、どの設計書にも入っていない工程成果物が無いか（入れないなら理由があるか）
- [ ] 同じ工程成果物が2冊に全文で入っていないか（1.5）
- [ ] 章ごとに由来が表示されているか（1.2）
- [ ] ID が工程成果物と同じか（1.3）
- [ ] 「該当なし」の章に理由が書かれているか（1.4）
- [ ] 事前提出版の場合、差し替え予定の章にその旨が書かれているか（3）
- [ ] 表紙の版・日付が組立時点のもので、構成要素ごとの版・日付が一覧になっているか

表紙の版は「組み立てた時点」を表すにすぎない。どの章がいつの実装から逆生成されたかは
構成要素ごとの版・日付でしか分からないため、構成要素の版表を巻末に付ける。

---

## 6. 品質・テスト系の納品物

テスト仕様書・テスト結果報告書・品質報告書などは27点に含まれない。これらは証跡パッケージ
（`reports/evidence/<タスクID>/`）から `doc-reverse-gen` Skill の `quality` 種別で作る。
組立定義に入れる場合は、構成要素として証跡パッケージのファイルを指定し、**証跡 / 参考所見 /
承認の3区分を章の中でも保つ**（区分の扱いは `plugin/skills/doc-reverse-gen/SKILL.md` を参照）。
