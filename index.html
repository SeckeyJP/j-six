01 J-SIX とは

日本の SI 業界で広く使われる V字モデル（ウォーターフォール）を、Claude Code（CC）の能力を前提に再設計した開発プロセス。従来モデルに AI を「貼り付ける」のではなく、世界標準の Spec-Driven Development（SDD）の原則を採りつつ、日本特有の品質基準・設計書文化・受発注構造に対応する 日本品質レイヤー を独自に設計している。

捨てるのではなく進化させる

V字モデルの品質基準は維持し、変えるのは「作り方」。既存案件を止めずに移行できる。

CC ネイティブ

外部フレームワークに依存せず、Claude Code の Skills / Agents / Hooks のみで構成。

正直な数値

主張には出典を付け、著者推定は「推定」と明記。実測と推定を切り分けて提示する。

02 4つの設計原則

原則 1

CC ネイティブ

BMAD 等の外部 FW に依存せず、Claude Code のネイティブ機能のみで構築する。

原則 2

3層ドキュメント

Spec（Why）+ ADR（Why Not）+ 逆生成設計書（What/How）で従来設計書を超える。

原則 3

TDD が品質の中核

テストファーストにより、CC の自律実行の品質を担保する。

原則 4

段階的移行

既存 V字モデルから3ステージで移行。既存案件を止めない。

自律度モデル L0（手動）〜 L4（完全自律）。v2.1 では L4 の条件を「自動テスト通過」から Phase 4 の G1〜G4 全層通過へ改めた（次節）。テストスイート単独を監督面にすると、それが最適化対象になり「テストは通るが意図を満たさない実装」が生じるため。

04 レビュー前の4層品質ゲート（v2.1）

人間レビューに出す前に、性質の異なる4つの監督面を順に通す。後段は前段を通過した場合のみ実行する（壊れたコードを LLM judge に見せない）。

層内容判定主体
G1 決定論的検証build / 型 / lint・format / SAST / secret scan / 依存脆弱性 / スコープ検査（変更ファイル ⊆ 許可リスト）script（終了コード）
G2 テスト品質検証全テスト通過 / カバレッジ / mutation score / テスト改変検出 / hold-out 受入テスト / トレーサビリティscript（終了コード）
G3 意図・スコープ判定正確性・要件未充足・スコープ逸脱のみを fresh context の judge が報告（スタイル指摘は禁止）LLM
G4 証跡パッケージG1〜G3 の結果を人間レビュー用・顧客納品用に構造化script ＋ LLM（要約のみ）

なぜテスト通過だけでは足りないか

監督面がテストスイート単独だと、エージェントはそれを検証手段ではなく最適化対象として扱う（reward hacking）。SpecBench は、可視テストと hold-out テストの pass 率の差でこれを定量化し、差はテスト網羅度ではなくタスク難度とモデル能力の差で拡大すると報告している。

L4 の条件を変更した

v2.0 の「L4＝人間は介入しない（自動テストのみ）」を、G1〜G4 全層通過を条件に介入しないへ改めた。テストのみの L4 は最も脆弱な構成である。

内側ループと外側ループ

Stop hook は8回連続ブロックで自動解除される。Hook は最終防衛線にならないため、同じ判定スクリプト・同じ設定で動く CI ゲート（外側ループ） を併設する。

証跡パッケージは「証跡（決定論的な生出力）／参考所見（AI の判定・要約）／承認（人間の記録）」の3区分を混ぜずに出力する。参考所見を単独で品質判定の根拠にしない。

05 3層ドキュメント戦略

「設計書はどうなるのか」という日本 SI 最大の関心に対する回答。コードを Source of Truth とし、コードから復元できない情報だけを人が書く。

第1層 — WHY

Spec（仕様）

なぜ作るか。業務背景・目的・要件。人が書き、合意する。

第2層 — WHY NOT

ADR（判断記録）

なぜその選択をしたか。検討した代替案と却下理由。

第3層 — WHAT / HOW

逆生成設計書

何をどう実装したか。コードから自動生成（例: OpenAPI）。

第3層はコードから逆生成されるため 設計書⇔コードの乖離が原理的にゼロ。一方、Why を記す第1・2層は逆生成できず人手更新のため乖離リスクが残る（→ 実証セクション参照）。

工程成果物27点と設計書への組立

第3層は「基本設計書」を直接生成しない。IPA「機能要件の合意形成ガイド」の工程成果物27点（システム振舞い・画面・データモデル・外部IF・バッチ・帳票）を単位に作り、組立定義に従って顧客様式の基本設計書・詳細設計書に束ねる。正は工程成果物で、設計書はそのビューである。

19

逆生成（コードから18・受入テストから1）

5

人手で書く（逆生成の前提になる）

3

コード＋Spec の併用

27点すべてを作る必要はない。事前に設計書を求める顧客には、章ごとに「事前提出できるか／納品時に逆生成版へ差し替えるか」を組立定義で決める。Phase 1・2・6 の品質ゲートには、合意形成ガイドの合意成熟度（仕掛／充実／完成）を到達基準として置いた。非機能要件は IPA 非機能要求グレードの6大項目で分類する。

07 期待効果と検証ステータス

J-SIX の数値は実測と推定を切り分けて扱う。実測 はケーススタディ等で検証済（ただしサンプル数は限定的）、推定 は著者推定で未実測。

ケーススタディ #2 — 「カバレッジ 99%」の mutation score

カバレッジは「テストが実行した行」を測るが、「テストが誤りを検出できるか」は測らない。同じコードで両方を実測して差を見た。

指標実測値意味
ステートメントカバレッジ99%207 stmt 中 未到達 2
mutation score（PBT 前）91.8%183 ミュータント中 15 生存
生存のうち本物のテストの穴3 件境界値 1 / 監査ログの操作者・理由 2
mutation score（PBT 後）93.4%性質テスト 8 件を追加し、狙った 3 件を正確に殺した

残る 12 件はエラーメッセージ文言と既定引数の変異で、外部から見た振る舞いを変えない。仕様が規定していない詳細をテストで固定すると脆いテストになるため、意図的に生かしている。mutation score 100% は目的ではない。

✅ 言えること

  • プロセスが小規模題材で実際に一周できる
  • テスト網羅・トレーサビリティ・IF 設計書の逆生成は実物として成立
  • カバレッジ品質ゲート（95%）を実測で充足
  • カバレッジ 99% でも本物のテストの穴が3件残っていた（うち2件は内部統制要件）
  • 生存ミュータントは性質テスト（PBT）の出発点として質が高い

⚠ 言えないこと

  • 「工数 60–70% 削減」は本ケースでも N=0 の推定のまま
  • 実証には「人手のみ」との A/B 工数比較が必要だが、実施は見送った（推定のまま扱う）
  • カバレッジ 99% / mutation 93.4% は N=1・小規模・外部依存なしで一般化不可
  • mutation の閾値 90% は本題材の実測値。他プロジェクトへは持ち込めない

再現: cd examples/approval-workflow && make test && make mutation && make gate ／ 詳細: docs/case-study-01.md, docs/case-study-02.md

その後の Plugin 実動検証 #1（2026-09-19）で同じ題材に TASK-AW-002 を実装し、現在の値はテスト 81 件＋hold-out 72 件、カバレッジ 99.0%、mutation score 92.4%、トレーサビリティ 21/21。

10 Claude Code Plugin（v2.1.0）

J-SIX の各 Phase を Claude Code のネイティブ機能で実装。Skills 7件・Agents 7件・Hooks に加え、LLM を介さない決定論的チェック 11本を同梱。Plugin は言語別ツールを直接呼ばず、標準フォーマット（JUnit XML / Cobertura・LCOV / SARIF / mutation-testing-elements JSON）のパースと閾値判定だけを行う。

Skills（7）
  • spec-create — 要求/Design Spec の対話的策定（P1–P2）
  • design-review — Spec・ADR・コード整合性検証（P2）
  • tdd-cycle — Hold-out→Red→Green→Refactor→G1〜G4（P4）
  • evidence-pack — 証跡パッケージへの要約付加（P4）新
  • quality-metrics — プロセス健全性の集計（P5）
  • doc-reverse-gen — 工程成果物の逆生成・設計書への組立・品質納品物（P6）
  • traceability — 要件→テスト→コード追跡（P1–P6）
Agents（7）
  • holdout-test-writer — hold-out 受入テスト作成 新
  • red-agent — テスト作成＋PROP から PBT＋RED タグ（P4）
  • green-agent — 最小実装のみ。テストに触れない（P4）
  • refactor-agent — 品質改善のみ（P4）
  • scope-judge — G3 意図・スコープ判定 新
  • qa-reviewer — 証跡の要約・探索的テスト観点（P5）
  • doc-generator — 工程成果物 → 組立 → 品質納品物の順に生成（P6）
Hooks
  • command型: 編集後（PostToolUse）に決定論的な format / lint（v2.0 の prompt 型を置換）
  • command型: Stop 時に品質ゲート G1→G4 を実行（オプトイン）
  • prompt型: ADR を記録すべき判断の検出のみ — 「停止してよいか」の評価器として記述
  • subagent スコープ: green-agent の tests/ 書込と hold-out 読取を拒否
決定論的チェック（11本）
  • jsix_run_checks.py — G1→G4 を順に実行。前段失敗で打ち切り
  • jsix_scope_check.py / jsix_sarif_gate.py — G1
  • jsix_junit_check.py / jsix_coverage_gate.py / jsix_mutation_gate.py — G2
  • jsix_test_tamper_check.py — G2: テスト弱体化の検出
  • jsix_traceability_check.py — G2: REQ / PROP ⇔ テスト
  • jsix_evidence_pack.py — G4: 証跡パッケージ生成
  • 既定はレポート駆動（成果物を読むだけ）。CI では --run-commands

実動検証: Skill 7本を claude -p --plugin-dir でヘッドレス実行し、単体テストでは見つからない Plugin の不具合8件（マニフェスト不正で Plugin 全体が読み込まれない、Stop hook がブロックし続ける等）を修正した（docs/plugin-field-test-01.md）。再発の検知には claude plugin eval の評価ケースを使う（plugin/evals/）。
