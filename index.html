01 J-SIX とは

日本の SI 業界で広く使われる V字モデル（ウォーターフォール）を、Claude Code（CC）の能力を前提に再設計した開発プロセス。従来モデルに AI を「貼り付ける」のではなく、世界標準の Spec-Driven Development（SDD）の原則を採りつつ、日本特有の品質基準・設計書文化・受発注構造に対応する 日本品質レイヤー を独自に設計している。

捨てるのではなく進化させる

V字モデルの品質基準は維持し、変えるのは「作り方」。既存案件を止めずに移行できる。

CC ネイティブ

外部フレームワークに依存せず、Claude Code の Skills / Agents / Hooks のみで構成。

正直な数値

主張には出典を付け、著者推定は「推定」と明記。実測と推定を切り分けて提示する。

02 4つの設計原則

原則 1

CC ネイティブ

BMAD 等の外部 FW に依存せず、Claude Code のネイティブ機能のみで構築する。

原則 2

3層ドキュメント

Spec（Why）+ ADR（Why Not）+ 逆生成設計書（What/How）で従来設計書を超える。

原則 3

TDD が品質の中核

テストファーストにより、CC の自律実行の品質を担保する。

原則 4

段階的移行

既存 V字モデルから3ステージで移行。既存案件を止めない。

04 3層ドキュメント戦略

「設計書はどうなるのか」という日本 SI 最大の関心に対する回答。コードを Source of Truth とし、コードから復元できない情報だけを人が書く。

第1層 — WHY

Spec（仕様）

なぜ作るか。業務背景・目的・要件。人が書き、合意する。

第2層 — WHY NOT

ADR（判断記録）

なぜその選択をしたか。検討した代替案と却下理由。

第3層 — WHAT / HOW

逆生成設計書

何をどう実装したか。コードから自動生成（例: OpenAPI）。

第3層はコードから逆生成されるため 設計書⇔コードの乖離が原理的にゼロ。一方、Why を記す第1・2層は逆生成できず人手更新のため乖離リスクが残る（→ 実証セクション参照）。

09 Claude Code Plugin（v2.1.0）

J-SIX の各 Phase を Claude Code のネイティブ機能で実装。Skills 6件・Agents 5件・Hooks に加え、LLM を介さない決定論的チェックを同梱。

Skills（6）
  • spec-create — 要求/Design Spec の対話的策定（P1–P2）
  • design-review — Spec・ADR・コード整合性検証（P2）
  • tdd-cycle — Red→Green→Refactor 管理（P4）
  • quality-metrics — メトリクス計測・品質ゲート（P5）
  • doc-reverse-gen — 設計書逆生成（P6）
  • traceability — 要件→テスト→コード追跡（P1–P6）
Agents（5）
  • red-agent — テスト作成のみ（P4）
  • green-agent — 最小実装のみ（P4）
  • refactor-agent — 品質改善のみ（P4）
  • qa-reviewer — 品質レビュー（読み取り専用）
  • doc-generator — 設計書一式の自動生成（P6）
Hooks
  • prompt型: 規約準拠チェック / テスト結果確認 / ADR 検出 / リトライ判断 / 権限拒否対応
  • command型（新）: Stop 時に決定論的品質ゲートを実行（オプトイン）
決定論的チェック（新）
  • jsix_traceability_check.py — 要件⇔テストの機械検証
  • jsix_coverage_gate.py — カバレッジ閾値判定
  • jsix_run_checks.py — .jsix-checks.json 同梱時のみ動く no-op 既定ランナー
