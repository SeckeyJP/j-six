## 指摘事項

### Critical（修正必須）

#### C-1. 状態遷移 API で対象が存在しないと 404 ではなく 409 を返す（Design Spec 4 章に違反）

- **Design Spec**: 4 章の末尾に「ドメインルール違反（`WorkflowError`）は HTTP 409 Conflict、対象不在は 404」とある。1 章の構成図にも「WorkflowError → HTTP 409/404 へ変換」とある。
- **実装**: `WorkflowService.get()` は対象がないときもルール違反と同じ `WorkflowError` を投げる（`app/workflow.py:44-48`）。
  404 に変換しているのは `GET /requests/{id}` だけで（`app/main.py:99-104`）、
  submit / approve / reject / remand / withdraw の 5 本は `_guard`（`app/main.py:76-80`）を通るため、一律に 409 になる。
- **影響**: 存在しない ID への操作が「競合」として返る。クライアントは「ID の誤り」と「状態の競合（再読込すれば解決しうる）」を区別できない。
- **根本原因**: `WorkflowError` という 1 つの例外に「不在」と「ルール違反」の 2 つの意味を持たせている。
  Design Spec 1 章の「WorkflowError → 409/404」も、1 つの例外から 2 種類のステータスを出す書き方になっていて、どう分けるかが決まっていない。
- **テストの抜け**: `tests/test_api.py` は GET の 404 しか確認していない。hold-out の `tests/acceptance/conftest.py` は「対象不在 404」を前提に書かれているが、状態遷移 API の不在ケースを確認するテストがない。
- **是正案**: Design Spec で「対象不在は専用の例外（例: `RequestNotFound(WorkflowError)`）とし、全エンドポイントで 404 に変換する」と決めて ADR に記録する（→ 不足 ADR-A）。
  Phase 4 で、全エンドポイントの 404 を確認するテストを先に書き、それから直す。
  4 章の表も、状態遷移の各行を「不在は 404 / ルール違反は 409」と書き分ける。

#### C-2. リクエストの入力項目が Design Spec にない。そのせいで `note` が受け付けられたまま捨てられている

- **Design Spec**: 4 章にはメソッド・パス・概要・異常時しかなく、リクエストボディの定義がない。
  3 章のドメインモデルにも `AuditEntry` の項目（action / actor / at / note）が書かれていない。
- **実装**: 5 本の状態遷移 API はどれも同じ `ActorBody { actor: str, note: str = "" }` を受ける（`app/main.py:29-31`）。
  ところがドメイン層に `note` を渡しているのは reject と remand だけで（`app/main.py:117-128`）、
  **submit / approve / withdraw は `note` を受け取っても 200 を返して捨てる**。
  実際に approve に「承認コメント」を付けて送ったところ、監査ログの APPROVE の `note` は空だった。
  OpenAPI（Swagger）には 5 本すべてに `note` が「コメント（任意）」として載るため、利用者は承認コメントが記録されると思い込む。
- **影響**: REQ-010 と J-SOX 対応（要求 Spec 4.3「承認の証跡保全が必須」）に関わる。
  利用者が残したつもりの承認・提出・取下げのコメントが証跡から消え、しかもエラーにならないので気づけない。
  さらに未定義のキー（例: `nte`）も黙って受理されるため、項目名を打ち間違えても気づけない。
- **是正案**: Design Spec 4 章に、エンドポイントごとの入力項目（必須/任意、型、制約）を書く。そのうえで次のどちらかを選び、合意する。
  1. 全操作で `note` を受け付け、監査ログに記録する（`approve` / `submit` / `withdraw` に `note` 引数を足す）
  2. `note` は reject / remand だけに限る。ほかの操作用のスキーマから `note` を外し、未定義キーは 422 で拒否する（`model_config = ConfigDict(extra="forbid")`）

  却下・差し戻しの理由を必須にするかどうかも、同じ節で決めておくとよい（今は任意で、空文字でも通る）。

### Warning（修正推奨）

#### W-1. 入力の形式エラー（422）とルール違反（409）の境目が決まっていない

型が違う入力（`amount: "abc"`）は Pydantic が 422 を返す。値が範囲外の入力（`amount: 0`）やタイトルが空の入力は、ドメインが 409 を返す。
Design Spec 4 章には 422 が出てこず、どちらの入力検証をどちらの層でやるかも書かれていない。
「金額は 1 以上」「タイトル必須」は業務ルールではなく入力制約なので、409 Conflict とするのは HTTP の意味から見ると不自然である。
422 / 400 / 409 の使い分けを 4 章で決めること。

#### W-2. 例外の変換先が文書ごとに違う

`WorkflowError` の docstring は「API 層で 400/409 に変換する」（`app/workflow.py:15`）、`main.py` の docstring は「409 に変換する」（`app/main.py:3`）、Design Spec は「409 / 不在は 404」と書いている。
400 を返す経路は実装にない。C-1 を直すときに、これらの記述も合わせてそろえること。

#### W-3. 性能要件（200ms）に設計側の対応がない

要求 Spec 3.5.2 では「API レスポンスタイム 200ms 以内」を目標値にしているのに、Design Spec 5.3 は「インメモリのため計測対象外」としている。
目標値が要求にある以上、「どの条件で 200ms を確認するか」または「本番化で合意するまで保留」を明記し、要求 Spec の記述とそろえること。

#### W-4. Design Spec に承認欄とステータスがない

要求 Spec には「Status: 承認済み」と承認欄があるが、Design Spec にはない。
Phase 2 の品質ゲートでは Design Spec が完成レベル（双方が確認済み）であることが求められるので、C-1 と C-2 を反映して版を上げたうえで、承認欄を設けること。

#### W-5. 逆生成版への差し替えの合意と組立定義がない

README の C2 表には「`app/` から IF 設計書（`/docs` Swagger）を生成可能」とあるが、Phase 6 で逆生成版に差し替えることの合意も、顧客に出す設計書の目次（`docs/design-docs/assembly-*.md`）もない。
C-2 のとおり、今の OpenAPI には実装と違う入力項目（捨てられる `note`）が載っているので、このまま逆生成すると IF 設計書に誤りが入る。

### Suggestion（検討推奨）

- **S-1. 成功時のステータスコードを定める**: 起票は 201、ほかは 200 だが、Design Spec には書かれていない（hold-out の conftest がこれを理由に 2xx で判定している）。IF 設計書を逆生成する前に明記したほうがよい。
- **S-2. 同時実行の前提を書く**: エンドポイントは同期関数なので、FastAPI のスレッドプールで並行に動く。`self._seq += 1` による採番や状態の更新にロックがなく、同時に起票すると ID が重複して前の申請（とその監査ログ）が上書きされうる。インメモリのサンプルなので、「単一ワーカー前提」と 5.2 に書くか、Repository 化の要件に含めるとよい。
- **S-3. actor の出どころを書く**: actor はリクエストボディで受け取り、そのまま信頼している。要求 Spec 5 章の前提（SSO が担保）と対応していることを Design Spec のセキュリティ欄に書いておくと、本番化でなりすまし対策を入れるときの差し替え点がはっきりする。
- **S-4. ドメインモデルの記述を補う**: 3 章には `next_approver`（算出する属性）と `AuditEntry` の項目がない。監査ログの形は REQ-010 の検証対象なので、項目まで書くこと。空文字の `applicant` / `actor` を拒否するかどうかも決めておくとよい（今は起票できてしまう）。
- **S-5. バージョン文字列を書かない**: 5.3 の「本書は v2.0 の構成で作成しており」は、リポジトリの品質ルール（ドキュメント内にバージョン文字列をハードコードしない）に反する。「旧テンプレートの構成で作成しており」などに言い換える。
