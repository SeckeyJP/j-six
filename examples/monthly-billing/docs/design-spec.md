## 1. アーキテクチャ概要

### 1.1 アーキテクチャスタイル

レイヤード（ドメイン層 / 出力層 / HTTP層 / バッチ層）。業務ルールはドメイン層
（`app/billing.py`）に集約し、他の層はそれを呼ぶだけにする。

**この構成にした理由**: 本システムの価値は消費税の端数処理（ADR-0001/0002）と締め処理の
正しさにある。これが画面・帳票・バッチ・会計連携の4つの入口から使われるため、ルールを
1箇所に置かないと入口ごとに実装がずれる。

### 1.2 システム構成図

```
                    ┌──────────────┐
  販売管理システム ──▶│ importer.py  │ EIF-002 売上取込（CSV）
                    └──────┬───────┘
                           ▼
  ┌────────────┐    ┌──────────────┐    ┌────────────┐
  │ main.py    │───▶│ billing.py   │◀───│ batch.py   │
  │ 画面 SCR   │    │ ドメイン      │    │ BATCH-001/2│
  └────────────┘    │ 締め・税計算  │    └────────────┘
                    └──────┬───────┘
                    ┌──────┴───────┐
                    ▼              ▼
             ┌────────────┐  ┌──────────────┐
             │ reports.py │  │ accounting.py│ EIF-001 会計連携
             │ RPT-001/2  │  └──────────────┘
             └────────────┘
```

### 1.3 技術スタック

| 分類 | 採用 | 理由 |
|---|---|---|
| 言語 | Python 3.9+ | `examples/approval-workflow` と揃える |
| Web | FastAPI | 同上 |
| 画面 | Jinja2（サーバサイドレンダリング） | 画面設計書の逆生成元がテンプレートとして残る |
| 帳票 | 印刷用 HTML ＋ CSV | ADR-0003 |
| 永続化 | なし（インメモリ） | サンプルのため。Repository を切り出して差し替え可能 |

**インメモリ実装の `reset()`**: `BillingService.reset(clock)` はストアを初期化する公開メソッド。
サンプルの再実行とテストのために置く。永続化実装に差し替えた場合は未サポートとしてよい。
| 金額計算 | `int`（円単位） | 浮動小数点の誤差を持ち込まない。ADR-0002 |

## 2. DB 設計

### 2.1 ER 概要

```
取引先(Customer) ──< 売上(SalesRecord)
      │
      └──< 請求(Invoice) ──< 請求明細(InvoiceLine)
                  │
                  └──< 税率別内訳(TaxSummary)
```

### 2.2 主要テーブル一覧

| エンティティ | 役割 | 主なキー |
|---|---|---|
| Customer | 取引先。締め日と支払サイトを持つ | customer_code |
| SalesRecord | 販売管理から取り込んだ売上明細 | record_id |
| Invoice | 請求。取引先×対象期間で1件 | invoice_no |
| InvoiceLine | 請求明細。**消費税額を持たない**（ADR-0001） | invoice_no + line_no |
| TaxSummary | 税率区分ごとの対価の額と消費税額 | invoice_no + tax_rate |

**TaxSummary を独立させた理由**: REQ-004/REQ-006 が税率ごとの区分記載を求めており、
端数処理の単位（ADR-0001）もこの粒度と一致する。明細に税額を持たせないことを
構造で表現している。

## 3. API 設計

### 3.1 API 一覧

| メソッド | パス | 概要 | 対応 |
|---|---|---|---|
| GET | `/invoices` | 請求一覧画面 | SCR-001 |
| GET | `/invoices/{invoice_no}` | 請求明細画面 | SCR-002 |
| GET | `/invoices/{invoice_no}/preview` | 請求書プレビュー画面 | SCR-003 |
| GET | `/invoices/{invoice_no}/report` | 請求書（印刷用 HTML） | RPT-001 |
| GET | `/invoices.csv` | 請求一覧表（CSV） | RPT-002 |
| GET | `/invoices.json` | 請求一覧（JSON） | SCR-001 のデータ源 |
| GET | `/invoices/{invoice_no}.json` | 請求明細（JSON） | SCR-002 のデータ源 |
| POST | `/invoices/{invoice_no}/confirm` | 請求の確定 | UC-006 |

**JSON エンドポイントを設けた理由**: 画面（SCR）は HTML を返すため、表示内容を機械的に
検証しようとすると HTML の文言に依存した脆いテストになる。画面が描画するデータそのものを
JSON でも公開し、**受入テストは JSON を、画面は HTML を**見る構成にする。両者が同じ
データ源を使うため、片方だけがずれることがない。

### 3.2 共通仕様

ドメインルール違反（`BillingError`）は HTTP 409 Conflict、対象不在は 404。
画面（SCR）は HTML、帳票（RPT）は `text/html` または `text/csv` を返す。

## 4. 画面設計

### 4.1 画面遷移

```
請求一覧(SCR-001) ──▶ 請求明細(SCR-002) ──▶ 請求書プレビュー(SCR-003)
        ▲                    │                        │
        └────────────────────┴────────────────────────┘
                          （戻る）
```

### 4.2 主要画面一覧

| 画面ID | 画面名 | 役割 |
|---|---|---|
| SCR-001 | 請求一覧 | 対象年月の請求を一覧表示。状態（未確定/確定済）で色分け |
| SCR-002 | 請求明細 | 明細行と税率別内訳を表示。確定操作の起点 |
| SCR-003 | 請求書プレビュー | 帳票 RPT-001 と同じ内容を画面で確認 |

**画面を SSR にした理由**: 画面設計書（画面レイアウト / 画面入出力項目一覧）の逆生成元が
Jinja2 テンプレートとして1箇所に残る。SPA にするとレイアウト情報がコンポーネントに
分散し、逆生成が難しくなる。

## 5. 外部 IF 設計

### 5.1 連携先一覧

| IF-ID | 連携先 | 方向 | 形式 | タイミング |
|---|---|---|---|---|
| EIF-001 | 会計システム | 送信 | CSV（ヘッダ行＋税率別内訳行） | 確定後、BATCH-002 で日次 |
| EIF-002 | 販売管理システム | 受信 | CSV | 日次 |

### 5.2 連携方針

ファイル連携（同期 API は使わない）。取込は冪等とし、同一 record_id の再取込は無視する。

## 6. セキュリティ設計

### 6.1 認証・認可

外部 SSO が担保する前提。本サンプルは actor を ID 文字列で受ける。

### 6.2 データ保護

請求金額と取引先名は機微情報として扱い、ログに明細内容を出力しない
（監査ログには件数と合計のみ記録する。REQ-010）。

---

## 7. 非機能設計

### 7.1 性能

インメモリのため本サンプルでは計測対象外。実装時は締め処理を取引先単位に分割できる
構造にしてある（`close_month` が取引先ごとにループする）。

### 7.3 監視・運用

締め処理の監査ログ（REQ-010）に実行日時・操作者・対象年月・作成件数を記録する。

## 8. Property（PROP）の実装方針

要求 Spec の `PROP-nnn` を property-based testing でどう検証するかを定める。

| 項目 | 内容 |
|---|---|
| PBT ライブラリ | Hypothesis（`examples/approval-workflow` と揃える） |
| 入力生成の戦略 | 金額は 1〜1,000,000 円の整数。税率は 10% / 8% の2値。明細件数は 1〜20 件。**端数が出る組合せを必ず含む**ため、金額は 10 で割り切れない値も生成する |
| 実行件数 | 既定（100）。CI でも同じ |
| 失敗時の扱い | 反例を最小化し、例ベースのテストとして固定してリグレッションにする |

| PROP ID | 検証方法 | 実装場所 |
|---|---|---|
| PROP-001 | PBT（任意の売上集合の総和） | `tests/test_properties.py` |
| PROP-002 | PBT（**明細ごとに丸めた額との差を検出する**） | 同上 |
| PROP-003 | PBT（税率別の対価の額の総和） | 同上 |
| PROP-004 | PBT（締め日 × 支払サイトの全組合せ） | 同上 |
| PROP-005 | PBT（取引先ごとの請求件数） | 同上 |
| PROP-006 | PBT（確定後の操作列） | 同上 |

**PROP-002 の書き方**: 「明細ごとに丸めて合計した額」と「請求単位で丸めた額」を両方
計算し、**後者が正である**ことを表明する。両者が一致する入力では何も検出できないため、
端数が出る入力を Hypothesis に探させるのがこの性質の要点である。
